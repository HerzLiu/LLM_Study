# 7.2.1 RAG 原理深入

⬅ [01-LLM评测体系](01-LLM%E8%AF%84%E6%B5%8B%E4%BD%93%E7%B3%BB.md)	|	➡ [03-Tiny-RAG实战速览](03-Tiny-RAG%E5%AE%9E%E6%88%98%E9%80%9F%E8%A7%88.md)

> ⭐ **本章核心理论**：RAG 是当下最火的 LLM 应用范式，缓解幻觉的杀手锏。

---

## 🎬 故事比喻：开卷考 vs 闭卷考

LLM 直接回答 = **闭卷考**
- 凭记忆答（预训练学到的知识）
- 不知道的就**瞎编**（[幻觉](../04-%E7%AC%AC4%E7%AB%A0-%E5%A4%A7%E8%AF%AD%E8%A8%80%E6%A8%A1%E5%9E%8B/03-LLM%E5%9B%9B%E5%A4%A7%E7%89%B9%E7%82%B9.md#%EF%B8%8F-%E7%89%B9%E7%82%B9-4%E6%8C%A5%E4%B9%8B%E4%B8%8D%E5%8E%BB%E7%9A%84%E5%B9%BB%E8%A7%89hallucination)）
- 数据**过时**（训练截止日期之后的事都不知道）

**RAG = 开卷考**
- 让 LLM **先查资料**（从知识库检索相关内容）
- **基于资料**回答（不是瞎编）
- 资料**随时可更新**（不用重训模型）

→ 同一个 LLM，开卷比闭卷靠谱得多。

---

## 🔥 RAG 解决 LLM 的 3 大痛点

| LLM 痛点           | RAG 的解法             |
| ---------------- | ------------------- |
| **幻觉**（一本正经胡说八道） | 让回答**基于真实文档** → 可追溯 |
| **知识过时**（截止训练日期） | 知识库**随时更新** → 实时性强  |
| **缺乏专业领域知识**     | 把领域知识库塞给 LLM → 不用重训 |

---

## 🏗 RAG 三步原理

> **RAG = Retrieval-Augmented Generation = 检索增强生成**

### 流程图

```
┌────────────────────────────────────────────────────┐
│         离线阶段（一次性做好）                       │
│                                                     │
│  文档库 → 切分 → Embedding → 向量数据库              │
│  (PDF/MD/TXT)                                       │
└────────────────────────────────────────────────────┘

┌────────────────────────────────────────────────────┐
│         在线阶段（每次查询）                          │
│                                                     │
│  用户问题                                            │
│     │                                                │
│     ▼                                                │
│  ① Embedding → 查询向量                              │
│     │                                                │
│     ▼                                                │
│  ② 向量数据库检索（余弦相似度找 top-k 文档）          │
│     │                                                │
│     ▼                                                │
│  ③ Prompt = "基于以下资料回答：[资料]\n问题：[Q]"     │
│     │                                                │
│     ▼                                                │
│  ④ LLM 生成回答（基于资料）                            │
└────────────────────────────────────────────────────┘
```

### 三个核心步骤

| 步骤                   | 干啥                 | 关键技术                  |
| -------------------- | ------------------ | --------------------- |
| **① 索引（Index）**      | 文档切片 + 向量化 + 存入向量库 | Tokenizer / Embedding |
| **② 检索（Retrieval）**  | 根据问题找相关文档          | 向量相似度（余弦）             |
| **③ 生成（Generation）** | LLM 基于检索到的文档生成答案   | Prompt 工程             |

## 🧠 关键概念深入

### 概念 1：Embedding（嵌入）

**作用**：把文本变成**稠密向量**（比如 1024 维）。

```
"今天天气真好" → [0.21, -0.43, 0.78, ..., 0.15]   # 1024 个数字
```

**特性**：
- 语义相近的文本，**向量距离也近**
- 比如 "今天天气好" 和 "今日晴朗" 向量距离很近
- 和 "我喜欢吃饺子" 距离就远

**常见 Embedding 模型**：
| 模型 | 维度 | 特点 |
|---|---|---|
| `text-embedding-3-small`（OpenAI） | 1536 | 通用 |
| **`BAAI/bge-m3`**（北智院） | 1024 | **中文友好，开源免费** |
| `BAAI/bge-large-zh-v1.5` | 1024 | 中文专项 |
| `m3e-base` | 768 | 中文 |

> 详见 [第 1 章词向量演进](../01-%E7%AC%AC1%E7%AB%A0-NLP%E5%9F%BA%E7%A1%80%E6%A6%82%E5%BF%B5/04-%E6%96%87%E6%9C%AC%E8%A1%A8%E7%A4%BA%E6%BC%94%E8%BF%9B.md)，Embedding 是 Word2Vec / BERT 思想的延续。

### 概念 2：余弦相似度

衡量两个向量"方向有多接近"：

$$\text{cos\_sim}(\vec{a}, \vec{b}) = \frac{\vec{a} \cdot \vec{b}}{\|\vec{a}\| \cdot \|\vec{b}\|}$$

| 值 | 含义 |
|---|---|
| 1.0 | 完全同方向（语义最相似） |
| 0.0 | 垂直（无关） |
| -1.0 | 反方向（语义相反） |

→ RAG 检索时，**找余弦相似度最高的 top-k 文档**。

### 概念 3：向量数据库

存储 (文本片段, 向量) 对，**支持高效相似度搜索**。

| 工具 | 类型 |
|---|---|
| **本地（轻量）** | FAISS / ChromaDB / Qdrant |
| **本地（生产）** | Milvus / Weaviate / Elasticsearch |
| **云服务** | Pinecone / Zilliz Cloud |

→ Tiny-RAG 自己实现一个简单的 → 见 [03-Tiny-RAG实战速览](03-Tiny-RAG%E5%AE%9E%E6%88%98%E9%80%9F%E8%A7%88.md)

### 概念 4：文档切分（Chunking）

**为什么要切？**
- 原文档可能几万字
- Embedding 模型有输入长度限制（通常 512~8K token）
- LLM 上下文也有限

**切分策略**：
| 策略 | 思路 |
|---|---|
| **按字数固定切** | 每 500 字一段（简单粗暴） |
| **按句子切** | `\n` 或句号分隔（保持语义完整） |
| **递归切分**（推荐） | 优先按段落 → 句子 → 字符 |
| **重叠切分** | 相邻段有 100~200 字重叠（防关键信息被截断） |

**实战经验**：
- `chunk_size = 500~1000` token
- `overlap = 100~200` token

## ⭐ RAG 完整 Prompt 模板

```python
RAG_PROMPT = """
使用以下上下文回答用户的问题。如果你不知道答案，就说你不知道。总是使用中文回答。

问题: {question}

可参考的上下文:
···
{context}
···

如果给定的上下文无法让你做出回答，请回答数据库中没有这个内容，你不知道。

有用的回答:
"""
```

→ **核心套路**：
1. 给 LLM 一段检索到的资料（context）
2. 明确**只能基于资料回答**
3. **明示"不知道就说不知道"** → 防止幻觉

## 🆚 RAG vs 微调（Fine-tuning）

很多人会问：**有了 RAG，还需要微调吗？**

| 维度 | **RAG** | **微调** |
|---|---|---|
| 主要解决 | 知识不足 / 不准 | 风格 / 格式 / 任务能力 |
| 成本 | 低（不用训模型） | 中~高 |
| 时效性 | 强（库随时更新） | 弱（重训才能更新） |
| 可追溯 | ✅ 答案有出处 | ❌ 黑箱 |
| 适合 | 知识型问答、客服、文档查询 | 学习角色、特定输出格式 |
| 缺点 | 检索不准则全错 | 学不到大量新知识 |

→ **二者互补**：实战常用 **微调 + RAG** 组合。

## 🔬 RAG 进阶变体（速览）

### Naive RAG（最基础，本章实战版）
- 检索 top-k → 拼到 prompt → 生成

### Advanced RAG
- **查询重写**：用 LLM 把用户问题改成更好的检索 query
- **多路检索 + Rerank**：用多种方式检索后，用 Rerank 模型重排
- **HyDE**：让 LLM 先生成假设性答案，再用答案去检索

### Modular RAG
- 把检索、生成、记忆等模块化
- 可灵活组合不同策略

### Agentic RAG ⭐
- 让 Agent **自主决定**：是否检索、检索几次、查哪些库
- 当前最前沿方向

## ⚠️ RAG 实战常见坑

1. **检索召回率低**
   - 切分太大/太小
   - Embedding 模型不匹配（如英文模型查中文）
   - 解法：调 chunk_size、换 embedding 模型、加 Rerank

2. **"看到资料还胡说"**
   - LLM 仍然忽略上下文
   - 解法：改 prompt（更强调"只能基于上下文"）、用更好的模型

3. **冗余文档干扰**
   - top-k 取太大，无关信息混入
   - 解法：调 k 值（一般 3~5）、加 Rerank 过滤

4. **长上下文**
   - 检索到的文档总长超过 LLM 上下文
   - 解法：先 LLM 摘要、用支持长上下文的模型

5. **多语言**
   - 中英文 Embedding 模型分离
   - 解法：用多语言 Embedding（如 `bge-m3`）

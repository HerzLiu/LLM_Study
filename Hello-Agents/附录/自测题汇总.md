## 第 1 章 初识智能体

→ 来自 [第 1 章总览](../01-%E7%AC%AC1%E7%AB%A0-%E5%88%9D%E8%AF%86%E6%99%BA%E8%83%BD%E4%BD%93/00-%E7%AB%A0%E8%8A%82%E6%80%BB%E8%A7%88.md)

### 题目

1. 分析以下 case 是否属于智能体,如果是,属于哪种类型(从多个维度):
   - **case A**:超级计算机(2 EFlop 算力)
   - **case B**:特斯拉自动驾驶检测障碍物
   - **case C**:AlphaGo 与人类对弈
   - **case D**:ChatGPT 智能客服处理投诉
2. 为"智能健身教练"设计 PEAS 模型,并分析环境特性(部分可观察/随机性/动态性等)
3. 电商退款审批:Workflow 方案 vs Agent 方案,各自优缺点?是否存在结合两者的方案 C?
4. 在 [1.3 旅行助手](../01-%E7%AC%AC1%E7%AB%A0-%E5%88%9D%E8%AF%86%E6%99%BA%E8%83%BD%E4%BD%93/03-%E5%8A%A8%E6%89%8B%E5%AE%9E%E7%8E%B0%E6%97%85%E8%A1%8C%E5%8A%A9%E6%89%8B.md)基础上加功能:记忆 / 备选方案 / 反思
5. 卡尼曼"系统 1 vs 系统 2"在 Agent 中如何对应?

<details>
<summary>👉 参考答案(点开)</summary>

**1.** 分析:
- **case A**:**不是 Agent** —— 超级计算机只是算力,没有感知-决策-行动闭环
- **case B**:**是 Agent** —— 反应式 + 基于模型 + 混合式(快速反应 + 长远规划)
- **case C**:**是 Agent** —— 学习型 + 规划式 + 基于效用(预想多步)
- **case D**:**是 LLM Agent** —— 规划与推理型 + 工具调用 + 反思
→ 详见 [01-什么是智能体](../01-%E7%AC%AC1%E7%AB%A0-%E5%88%9D%E8%AF%86%E6%99%BA%E8%83%BD%E4%BD%93/01-%E4%BB%80%E4%B9%88%E6%98%AF%E6%99%BA%E8%83%BD%E4%BD%93.md)

**2.** 智能健身教练 PEAS:
- **P**: 健身目标达成率、用户安全、坚持率
- **E**: 用户身体 + 健身房环境 + 历史训练数据
- **A**: 语音指导 / 调整训练计划 / 推送饮食建议
- **S**: 心率传感器 / 摄像头(动作识别)/ 用户输入
- **特性**: 部分可观察(看不到全部生理状态)+ 随机(用户状态变化)+ 多智能体(医生/营养师协同)+ 动态(身体一直变)
→ 详见 [02-构成与运行原理](../01-%E7%AC%AC1%E7%AB%A0-%E5%88%9D%E8%AF%86%E6%99%BA%E8%83%BD%E4%BD%93/02-%E6%9E%84%E6%88%90%E4%B8%8E%E8%BF%90%E8%A1%8C%E5%8E%9F%E7%90%86.md)

**3.** 退款审批:
- **Workflow 优点**: 快、稳、低成本、可审计;**缺点**: 不灵活,异常处理差
- **Agent 优点**: 灵活、能处理边界情况;**缺点**: 慢、贵、可能出错
- **方案 C**: 混合 —— **Workflow 做主框架**(快速通道),**Agent 处理疑难案例**(>500RMB 或异常)
→ 详见 [04-两种协作模式与Workflow对比](../01-%E7%AC%AC1%E7%AB%A0-%E5%88%9D%E8%AF%86%E6%99%BA%E8%83%BD%E4%BD%93/04-%E4%B8%A4%E7%A7%8D%E5%8D%8F%E4%BD%9C%E6%A8%A1%E5%BC%8F%E4%B8%8EWorkflow%E5%AF%B9%E6%AF%94.md)

**4.** 加功能思路:
- **记忆**: prompt_history 增加用户偏好字段,跨会话用向量数据库存
- **备选方案**: 在 prompt 里加"如失败 try 备选"指令,Action 增加 `try_alternative`
- **反思**: 加 Reflection 智能体,N 次拒绝后让 LLM 总结失败原因,调整策略
→ 这本质上是 ReAct + Reflection,详见 [第 4 章 ReAct](../04-%E7%AC%AC4%E7%AB%A0-%E6%99%BA%E8%83%BD%E4%BD%93%E7%BB%8F%E5%85%B8%E8%8C%83%E5%BC%8F/02-ReAct%E8%8C%83%E5%BC%8F.md) 和 [Reflection 范式](../04-%E7%AC%AC4%E7%AB%A0-%E6%99%BA%E8%83%BD%E4%BD%93%E7%BB%8F%E5%85%B8%E8%8C%83%E5%BC%8F/04-Reflection%E8%8C%83%E5%BC%8F.md)

**5.** 卡尼曼双系统对应:
- **系统 1(快速直觉)** = **LLM 的直接输出** —— 看到问题直接给答案
- **系统 2(慢速推理)** = **Thought + 工具调用 + 反思** —— 显式推理过程
- 当前 LLM Agent 试图把两者结合:简单问题走系统 1,复杂问题启动系统 2
→ 详见 [1.1.3 神经符号主义](../01-%E7%AC%AC1%E7%AB%A0-%E5%88%9D%E8%AF%86%E6%99%BA%E8%83%BD%E4%BD%93/01-%E4%BB%80%E4%B9%88%E6%98%AF%E6%99%BA%E8%83%BD%E4%BD%93.md)

</details>

## 第 2 章 智能体发展史

→ 来自 [第 2 章总览](../02-%E7%AC%AC2%E7%AB%A0-%E6%99%BA%E8%83%BD%E4%BD%93%E5%8F%91%E5%B1%95%E5%8F%B2/00-%E7%AB%A0%E8%8A%82%E6%80%BB%E8%A7%88.md)

### 题目

1. 物理符号系统假说(PSSH):
   - "充分性论断" vs "必要性论断"是什么?
   - 符号主义实践挑战如何反驳"充分性"?
   - LLM Agent 是否符合 PSSH?
2. MYCIN 为何没大规模临床应用?如果让你重新设计医疗 Agent,如何克服 MYCIN 局限?
3. 扩展 ELIZA:加 5 条新规则、加上下文记忆;与 ChatGPT 对比 3 个本质差异
4. 心智社会:
   - "GRASP 失效"会怎样?去中心化优劣?
   - 与现代多 Agent 框架(CrewAI/MetaGPT)的关联?
   - LLM 时代心智社会还适用吗?
5. 强化学习 vs 监督学习:本质区别?数据需求?LLM 训练里 RL 起了什么作用?
6. 预训练为什么解决了"知识获取瓶颈"?会被新范式取代吗?
7. 设计"智能代码审查助手":
   - 在 1980s 符号时代怎么做?
   - 在 2015 深度学习时代怎么做?
   - 在当前 LLM 时代怎么做?

<details>
<summary>👉 参考答案(点开)</summary>

**1.** PSSH:
- **充分性**: 物理符号系统**足够**产生通用智能
- **必要性**: 通用智能**必须**是物理符号系统
- 符号主义挑战(知识瓶颈/常识/框架/脆弱性)反驳了充分性 —— 实践证明"只靠符号操作不够"
- LLM Agent 部分符合:神经网络层面是亚符号,但**输出的 Thought-Action 是符号** —— 神经符号融合
→ 详见 [01-符号主义早期智能体](../02-%E7%AC%AC2%E7%AB%A0-%E6%99%BA%E8%83%BD%E4%BD%93%E5%8F%91%E5%B1%95%E5%8F%B2/01-%E7%AC%A6%E5%8F%B7%E4%B8%BB%E4%B9%89%E6%97%A9%E6%9C%9F%E6%99%BA%E8%83%BD%E4%BD%93.md)

**2.** MYCIN 未临床原因:
- **法律责任**: 出错谁负责?
- **伦理**: 医生不信任 AI 决策
- **可解释**(虽然 MYCIN 已经比黑盒好)
- **维护成本**: 规则要随医学进展不断更新
- 现代设计: **LLM + 知识图谱 + RAG + 人机协同**(AI 辅助决策,医生最终拍板)
→ 详见 [01-符号主义早期智能体](../02-%E7%AC%AC2%E7%AB%A0-%E6%99%BA%E8%83%BD%E4%BD%93%E5%8F%91%E5%B1%95%E5%8F%B2/01-%E7%AC%A6%E5%8F%B7%E4%B8%BB%E4%B9%89%E6%97%A9%E6%9C%9F%E6%99%BA%E8%83%BD%E4%BD%93.md)

**3.** 扩展 ELIZA:
- 加 5 条规则不难(改 [2.2 代码](../02-%E7%AC%AC2%E7%AB%A0-%E6%99%BA%E8%83%BD%E4%BD%93%E5%8F%91%E5%B1%95%E5%8F%B2/02-ELIZA%E4%B8%8E%E8%A7%84%E5%88%99%E7%B3%BB%E7%BB%9F.md))
- 加上下文: 用全局 dict 存提取到的关键信息(姓名、职业等),在规则模板里引用
- 与 ChatGPT 差异:
  - **语义理解**: ELIZA 无,ChatGPT 有
  - **上下文**: ELIZA 单句,ChatGPT 长上下文
  - **泛化**: ELIZA 规则外失灵,ChatGPT 涌现能力
- 数学说明组合爆炸: N 个槽位 × M 种填法 = O(M^N) 规则
→ 详见 [02-ELIZA与规则系统](../02-%E7%AC%AC2%E7%AB%A0-%E6%99%BA%E8%83%BD%E4%BD%93%E5%8F%91%E5%B1%95%E5%8F%B2/02-ELIZA%E4%B8%8E%E8%A7%84%E5%88%99%E7%B3%BB%E7%BB%9F.md)

**4.** 心智社会:
- GRASP 失效 → BUILD-TOWER 整个系统瘫痪(去中心化的脆弱面)
- 优势: **容错性**(部分功能失效不影响其他)、**可扩展**(加新 Agent 即可)
- 劣势: **协调难**、**没全局规划**、**关键节点失效会瘫痪**
- 与 CrewAI/MetaGPT 关联: 都是**分工 + 涌现** —— 思想完全一致
- LLM 时代仍适用:**核心思想是分工协作 + 涌现**,只是单元从"无心算子"换成"LLM 智能体"
→ 详见 [03-心智社会](../02-%E7%AC%AC2%E7%AB%A0-%E6%99%BA%E8%83%BD%E4%BD%93%E5%8F%91%E5%B1%95%E5%8F%B2/03-%E5%BF%83%E6%99%BA%E7%A4%BE%E4%BC%9A.md)

**5.** RL vs 监督学习:
- **本质区别**: 监督学习从**标注数据**学;RL 从**与环境交互的反馈**学
- **数据需求**: 监督要标注;RL 要环境/模拟器
- LLM 训练中 RL 的作用:**RLHF / DPO / GRPO** —— 对齐人类偏好,提升推理
- 详见 [Happy-LLM RLHF](../../Happy-LLM/04-%E7%AC%AC4%E7%AB%A0-%E5%A4%A7%E8%AF%AD%E8%A8%80%E6%A8%A1%E5%9E%8B/07-RLHF%E4%BA%BA%E7%B1%BB%E5%8F%8D%E9%A6%88%E5%BC%BA%E5%8C%96%E5%AD%A6%E4%B9%A0.md)

**6.** 预训练解决知识瓶颈:
- 不需要手工编码,**从互联网文本自动学**
- 知识表示方式: 符号(明确规则)vs 连接权重(分布式)
- 互联网数据可能带偏见 / 错误 / 隐私问题,需 **数据清洗 + 对齐**
- 未来可能被取代但**短期内是主流** —— 候选方向: **多模态预训练 / 世界模型 / 推理模型**
→ 详见 [04-学习范式演进](../02-%E7%AC%AC2%E7%AB%A0-%E6%99%BA%E8%83%BD%E4%BD%93%E5%8F%91%E5%B1%95%E5%8F%B2/04-%E5%AD%A6%E4%B9%A0%E8%8C%83%E5%BC%8F%E6%BC%94%E8%BF%9B.md)

**7.** 智能代码审查助手:
- **1980s(符号时代)**: 用规则 + 语法树检查 lint 错误 —— 能做静态检查,**无法理解语义**
- **2015(深度学习时代)**: 训分类模型识别 bug 模式 —— 比规则强,但需要大量标注数据
- **当前(LLM 时代)**: LLM + 代码理解 + 工具调用(git diff/编译器/测试运行)+ 反思 —— 接近人类 Code Reviewer
- 架构: 感知(PR 内容)→ 规划(分模块审查)→ LLM 推理 → 工具调用(运行测试)→ 输出报告
→ 详见 [04-学习范式演进](../02-%E7%AC%AC2%E7%AB%A0-%E6%99%BA%E8%83%BD%E4%BD%93%E5%8F%91%E5%B1%95%E5%8F%B2/04-%E5%AD%A6%E4%B9%A0%E8%8C%83%E5%BC%8F%E6%BC%94%E8%BF%9B.md)

</details>

## 第 3 章 大语言模型基础

→ 来自 [第 3 章总览](../03-%E7%AC%AC3%E7%AB%A0-%E5%A4%A7%E8%AF%AD%E8%A8%80%E6%A8%A1%E5%9E%8B%E5%9F%BA%E7%A1%80/00-%E7%AB%A0%E8%8A%82%E6%80%BB%E8%A7%88.md)

### 题目

1. N-gram 模型的两大缺陷是什么?为什么神经网络能解决?
2. Decoder-Only 架构相比原版 Transformer 简化在哪?为什么"简化"反而成了主流?
3. 做 Agent 时 `temperature` 该设多少?为什么?
4. 解释 Top-k vs Top-p 的本质区别。
5. 同样意思,中文比英文费 Token 几倍?为什么这影响 Agent 成本?
6. LLM 的"幻觉"对 Agent 有什么影响?有哪些缓解方法?
7. Scaling Law 对 Agent 选型有什么启示?为什么 7B 是个临界点?

<details>
<summary>👉 参考答案(点开)</summary>

**1.** N-gram 两大缺陷:
- **数据稀疏**:没见过的组合概率为 0
- **泛化能力差**:不理解词的语义相似性("agent" 和 "robot" 在 N-gram 看来无关)
神经网络通过**词嵌入(连续向量)**解决:语义相近的词向量也相近。
→ 详见 [01-LLM架构速览](../03-%E7%AC%AC3%E7%AB%A0-%E5%A4%A7%E8%AF%AD%E8%A8%80%E6%A8%A1%E5%9E%8B%E5%9F%BA%E7%A1%80/01-LLM%E6%9E%B6%E6%9E%84%E9%80%9F%E8%A7%88.md)

**2.** Decoder-Only 简化:
- 抛弃 Encoder
- 无交叉注意力
- 只保留掩码自注意力 + Decoder 模块
"简化"成主流的原因:
- 训练目标统一(都是预测下一个 token)
- 结构简单易扩展(千亿参数也能扛)
- 天然适合生成任务(对话/写作/代码都是生成)
→ 详见 [Happy-LLM GPT 详解](../../Happy-LLM/03-%E7%AC%AC3%E7%AB%A0-%E9%A2%84%E8%AE%AD%E7%BB%83%E8%AF%AD%E8%A8%80%E6%A8%A1%E5%9E%8B/06-GPT.md)

**3.** Agent 用 **`temperature=0` 或 0.1~0.3**:
- Agent 工具调用需要**稳定可预测**输出
- 高温度 → LLM 输出格式不稳 → 解析失败
- 工具参数错乱 → Agent 崩
→ 详见 [3.2.1](../03-%E7%AC%AC3%E7%AB%A0-%E5%A4%A7%E8%AF%AD%E8%A8%80%E6%A8%A1%E5%9E%8B%E5%9F%BA%E7%A1%80/02-%E4%B8%8ELLM%E4%BA%A4%E4%BA%92.md#%E6%97%8B%E9%92%AE-1temperature%E6%B8%A9%E5%BA%A6)

**4.** Top-k vs Top-p:
- **Top-k**:**固定**选概率前 k 个候选
- **Top-p**:**动态**累加概率到 p,候选数自适应
**本质区别**:Top-p 对**分布不均匀的极端情况**适应性更好(长尾分布)
→ 详见 [Happy-LLM 采样策略](../../Happy-LLM/05-%E7%AC%AC5%E7%AB%A0-%E5%8A%A8%E6%89%8B%E6%90%AD%E5%BB%BA%E5%A4%A7%E6%A8%A1%E5%9E%8B/11-%E7%94%9F%E6%88%90%E6%96%87%E6%9C%AC.md#-%E9%87%87%E6%A0%B7%E7%AD%96%E7%95%A5%E8%AF%A6%E8%A7%A3)

**5.** 中文比英文费 Token **2~3 倍**:
- 英文 1 单词 ≈ 1 Token
- 中文 1 字 ≈ 1-2 Token
对 Agent 成本影响:
- API 按 Token 计费
- 同样的多轮对话,中文成本 2-3 倍
- 长上下文(如 RAG)中文消耗更快
→ 详见 [3.2.3](../03-%E7%AC%AC3%E7%AB%A0-%E5%A4%A7%E8%AF%AD%E8%A8%80%E6%A8%A1%E5%9E%8B%E5%9F%BA%E7%A1%80/02-%E4%B8%8ELLM%E4%BA%A4%E4%BA%92.md#-323-%E6%96%87%E6%9C%AC%E5%88%86%E8%AF%8D%E5%BD%B1%E5%93%8D-agent-%E6%88%90%E6%9C%AC%E7%9A%84%E5%85%B3%E9%94%AE)

**6.** 幻觉对 Agent 影响:
- 知识问答 Agent:**编不存在的事实**(影响极大)
- 代码 Agent:**编不存在的 API**
- 多步规划 Agent:**基于错误前提规划**(全错)
**缓解方法**(5 大法宝):
- **RAG**:检索真实文档
- **工具调用**:用真实 API,不靠记忆
- **Reflection**:自我反思 + 纠错
- **温度调低**(0)
- **结构化输出**(Function Calling)
→ 详见 [3.3.2](../03-%E7%AC%AC3%E7%AB%A0-%E5%A4%A7%E8%AF%AD%E8%A8%80%E6%A8%A1%E5%9E%8B%E5%9F%BA%E7%A1%80/03-%E7%BC%A9%E6%94%BE%E6%B3%95%E5%88%99%E4%B8%8E%E5%B1%80%E9%99%90.md#%EF%B8%8F-332-%E6%A8%A1%E5%9E%8B%E5%B9%BB%E8%A7%89hallucination-agent-%E7%9A%84%E5%A4%A9%E6%95%8C)

**7.** Scaling Law 对 Agent 启示:
- 模型**越大**,涌现能力**越强**
- **CoT、few-shot 等都是涌现能力**,只在大模型才有
**7B 是临界点**因为:
- < 7B:简单工具调用可以,但多步推理不行
- 7B+:开始有像样的推理能力,可做 Agent 主力
- **做生产级 Agent 至少 7B 起,推荐 30B+**

## 第 4 章 智能体经典范式

→ 来自 [第 4 章总览](../04-%E7%AC%AC4%E7%AB%A0-%E6%99%BA%E8%83%BD%E4%BD%93%E7%BB%8F%E5%85%B8%E8%8C%83%E5%BC%8F/00-%E7%AB%A0%E8%8A%82%E6%80%BB%E8%A7%88.md)

### 题目

1. ReAct = Reasoning + Acting,为什么"思考 + 行动"比纯思考(CoT)或纯行动好?
2. ReAct 的 `max_steps` 为什么必须设?设多少合适?
3. Plan-and-Solve 解决了 ReAct 的什么痛点?它又有什么自己的局限?
4. 为什么 Planner 用 `ast.literal_eval` 而不是 `eval` 解析输出?
5. Reflection 范式中,Executor 用 `temperature=0.7`,Critic 用 `temperature=0`,为什么?
6. Reflection 的"早停机制"是什么?为什么重要?
7. 实战中三大范式可以组合使用吗?给一个组合方案的例子。
8. 你要做一个"自动写周报"的 Agent,该选哪种范式?为什么?

<details>
<summary>👉 参考答案(点开)</summary>

**1.** ReAct vs 纯思考 vs 纯行动:
- **纯思考(CoT)**:无法访问外部世界 → **幻觉严重**
- **纯行动**:LLM 直接输出动作 → **缺乏规划和纠错**
- **ReAct**:思考**指导**行动 + 行动结果**修正**思考 → **1+1>2**
→ 详见 [4.2.1](../04-%E7%AC%AC4%E7%AB%A0-%E6%99%BA%E8%83%BD%E4%BD%93%E7%BB%8F%E5%85%B8%E8%8C%83%E5%BC%8F/02-ReAct%E8%8C%83%E5%BC%8F.md#-421-react-%E4%B9%8B%E5%89%8D%E7%9A%84%E4%B8%A4%E4%B8%AA%E5%AF%B9%E6%AF%94%E6%B4%BE)

**2.** `max_steps` 必设的原因:
- **防死循环** —— LLM 可能反复调同一个工具卡住
- **防止烧钱** —— 死循环的 Agent 每秒钟在花钱
- **及时止损** —— 几次尝试都失败,说明任务有问题
**合适值**:简单任务 5,复杂任务 10-20,**生产用 30 封顶**。
→ 详见 [[../04-第4章-智能体经典范式/02-ReAct范式#🔑 关键 1:**`max_steps` 是安全阀**|4.2.5]]

**3.** Plan-and-Solve 解决的痛点:
- ReAct 的**短视** + **可能陷入原地打转**
- 缺乏**全局规划**
P&S 自己的局限:
- **计划僵化**(中途遇变化难调整)
- **首次规划压力大**(Planner 要一次想清所有步骤)
- **计划错则全错**
→ 详见 [4.3.8](../04-%E7%AC%AC4%E7%AB%A0-%E6%99%BA%E8%83%BD%E4%BD%93%E7%BB%8F%E5%85%B8%E8%8C%83%E5%BC%8F/03-Plan-and-Solve%E8%8C%83%E5%BC%8F.md#-438-plan-and-solve-%E7%9A%84%E4%BC%98%E5%8A%BF%E4%B8%8E%E5%B1%80%E9%99%90)

**4.** `ast.literal_eval` vs `eval`:
- `eval()` 会**执行任意 Python 代码**(LLM 输出恶意代码会被执行,**安全风险**)
- `ast.literal_eval()` **只接受字面值**(列表/字典/数字/字符串),遇到代码会**报错**
**生产代码永远别用 `eval()` 解析 LLM 输出**!
→ 详见 [[../04-第4章-智能体经典范式/03-Plan-and-Solve范式#🔑 为什么用 `ast.literal_eval` 而不是 `eval`?|4.3.4]]

**5.** Reflection 的 temperature 差异化:
- **Executor (0.7)** —— 创作需要**有创意**
- **Critic (0.0)** —— 反思需要**严谨稳定**(找出真问题,不要瞎找)
- **Refiner (0.7)** —— 修订也是创作,**保留创意 + 加入改进**
→ 不同角色用不同 temperature 是工程关键细节
→ 详见 [4.4.4](../04-%E7%AC%AC4%E7%AB%A0-%E6%99%BA%E8%83%BD%E4%BD%93%E7%BB%8F%E5%85%B8%E8%8C%83%E5%BC%8F/04-Reflection%E8%8C%83%E5%BC%8F.md#-%E5%85%B3%E9%94%AE-2temperature-%E7%9A%84%E7%B2%BE%E5%A6%99%E8%AE%BE%E8%AE%A1)

**6.** 早停机制:
- 检测 Critic 输出包含"无需修改"等关键词 → **立即退出循环**
**重要性**:
- 防止**无限优化**(每轮都浪费 token)
- 反思员认为完美就该停
- 避免**过度修订**(可能越改越差)
→ 详见 [4.4.4](../04-%E7%AC%AC4%E7%AB%A0-%E6%99%BA%E8%83%BD%E4%BD%93%E7%BB%8F%E5%85%B8%E8%8C%83%E5%BC%8F/04-Reflection%E8%8C%83%E5%BC%8F.md#-%E5%85%B3%E9%94%AE-3%E6%97%A9%E5%81%9C%E6%9C%BA%E5%88%B6early-stop)

**7.** 三大范式可以组合,常见组合:
- **Plan + ReAct 子任务**:高层用 Plan,每个子任务用 ReAct
- **ReAct + Reflection**:工具调用后反思结果
- **Plan + Reflection**:执行完成后反思整体
- **多 Agent + Reflection**:一个做、一个评
**例子**:**论文助手** = Plan(规划结构)+ ReAct(查资料 + 写作)+ Reflection(终稿打磨)
→ 详见 [4.5](../04-%E7%AC%AC4%E7%AB%A0-%E6%99%BA%E8%83%BD%E4%BD%93%E7%BB%8F%E5%85%B8%E8%8C%83%E5%BC%8F/05-%E4%B8%89%E5%A4%A7%E8%8C%83%E5%BC%8F%E5%AF%B9%E6%AF%94.md#-%E7%9C%9F%E5%AE%9E%E5%9C%BA%E6%99%AF%E5%BA%94%E7%94%A8)

**8.** 自动写周报 Agent:
- **任务性质**:有固定结构(本周完成/下周计划/问题)+ 需要查资料(commit/PR/Issue)+ 质量要求中等
- **推荐方案**: **Plan + ReAct**
  - Plan: 规划周报结构(Section 1/2/3)
  - ReAct: 每个 Section 调 GitHub API 获取实际数据
- **可选加 Reflection**: 写完后**自查格式 + 措辞**
→ 详见 [4.5 决策树](../04-%E7%AC%AC4%E7%AB%A0-%E6%99%BA%E8%83%BD%E4%BD%93%E7%BB%8F%E5%85%B8%E8%8C%83%E5%BC%8F/05-%E4%B8%89%E5%A4%A7%E8%8C%83%E5%BC%8F%E5%AF%B9%E6%AF%94.md#-%E9%80%89%E5%9E%8B%E5%86%B3%E7%AD%96%E6%A0%91)

</details>

## 第 5 章 基于低代码平台的智能体搭建

→ 来自 [第 5 章总览](../05-%E7%AC%AC5%E7%AB%A0-%E5%9F%BA%E4%BA%8E%E4%BD%8E%E4%BB%A3%E7%A0%81%E5%B9%B3%E5%8F%B0%E7%9A%84%E6%99%BA%E8%83%BD%E4%BD%93%E6%90%AD%E5%BB%BA/00-%E7%AB%A0%E8%8A%82%E6%80%BB%E8%A7%88.md)

### 题目

1. 为什么需要低代码平台?它和"框架"、"纯代码"是什么关系?
2. Coze、Dify、n8n 三者各自定位有什么本质差异?

7. 你的企业要做"内部 AI 文档问答 + 流程自动化",该选啥?

<details>
<summary>👉 参考答案(点开)</summary>

**1.** 低代码平台**降低技术门槛 + 提升开发效率 + 可视化 + 沉淀最佳实践**。
关系:**互补不替代** —— 平台 = 最高层抽象,框架 = 中层,代码 = 底层。
真实生产**三者常组合使用**(原型用平台 → 框架做定制 → 代码做极致优化)。
→ 详见 [01-为什么需要低代码平台](../05-%E7%AC%AC5%E7%AB%A0-%E5%9F%BA%E4%BA%8E%E4%BD%8E%E4%BB%A3%E7%A0%81%E5%B9%B3%E5%8F%B0%E7%9A%84%E6%99%BA%E8%83%BD%E4%BD%93%E6%90%AD%E5%BB%BA/01-%E4%B8%BA%E4%BB%80%E4%B9%88%E9%9C%80%E8%A6%81%E4%BD%8E%E4%BB%A3%E7%A0%81%E5%B9%B3%E5%8F%B0.md)

**2.** 三者定位:
- **Coze**:零代码 Agent 平台(主体是 AI Agent)
- **Dify**:开源全栈 LLM 应用平台(主体是 AI Agent + RAG + MCP)
- **n8n**:**通用工作流自动化** —— LLM 只是其中一个节点(主体是 Workflow)
→ 详见 [三大平台速览](../05-%E7%AC%AC5%E7%AB%A0-%E5%9F%BA%E4%BA%8E%E4%BD%8E%E4%BB%A3%E7%A0%81%E5%B9%B3%E5%8F%B0%E7%9A%84%E6%99%BA%E8%83%BD%E4%BD%93%E6%90%AD%E5%BB%BA/01-%E4%B8%BA%E4%BB%80%E4%B9%88%E9%9C%80%E8%A6%81%E4%BD%8E%E4%BB%A3%E7%A0%81%E5%B9%B3%E5%8F%B0.md#-512-%E5%BD%93%E5%89%8D%E4%B8%89%E5%A4%A7%E4%B8%BB%E6%B5%81%E5%B9%B3%E5%8F%B0%E9%80%9F%E8%A7%88)

**3.** Coze 最致命的短板是**不支持 MCP**。
为什么是大问题:
- **MCP 是行业大势所趋**(OpenAI/Anthropic 都支持)
- 不支持 MCP → **锁在 Coze 自家插件生态**
- 未来想接入新工具会**受限**
→ 详见 [Coze 局限](../05-%E7%AC%AC5%E7%AB%A0-%E5%9F%BA%E4%BA%8E%E4%BD%8E%E4%BB%A3%E7%A0%81%E5%B9%B3%E5%8F%B0%E7%9A%84%E6%99%BA%E8%83%BD%E4%BD%93%E6%90%AD%E5%BB%BA/02-Coze-%E5%AD%97%E8%8A%82%E9%9B%B6%E4%BB%A3%E7%A0%81%E7%8E%8B%E8%80%85.md#%EF%B8%8F-%E5%B1%80%E9%99%90)

**4.** Dify 4 大杀手锏:
- **模型中立**(GPT/DeepSeek/Llama 任意切换)
- **本地部署**(数据不出企业内网)
- **支持 MCP**(接入新兴生态)
- **开源**(不被 vendor lock-in)
→ 详见 [03-Dify-开源全栈平台](../05-%E7%AC%AC5%E7%AB%A0-%E5%9F%BA%E4%BA%8E%E4%BD%8E%E4%BB%A3%E7%A0%81%E5%B9%B3%E5%8F%B0%E7%9A%84%E6%99%BA%E8%83%BD%E4%BD%93%E6%90%AD%E5%BB%BA/03-Dify-%E5%BC%80%E6%BA%90%E5%85%A8%E6%A0%88%E5%B9%B3%E5%8F%B0.md)

**5.** n8n 最大差异:**主体是工作流(Workflow),AI 只是其中一个节点**(其他框架/平台主体都是 Agent)。
适合场景:
- 已经用了一堆 SaaS 工具(Notion/Slack/Gmail/数据库)
- 想把 AI **嵌入现有业务流程**
- 需要复杂的触发器(Webhook/定时/数据库变化)
→ 详见 [04-n8n-通用自动化加AI](../05-%E7%AC%AC5%E7%AB%A0-%E5%9F%BA%E4%BA%8E%E4%BD%8E%E4%BB%A3%E7%A0%81%E5%B9%B3%E5%8F%B0%E7%9A%84%E6%99%BA%E8%83%BD%E4%BD%93%E6%90%AD%E5%BB%BA/04-n8n-%E9%80%9A%E7%94%A8%E8%87%AA%E5%8A%A8%E5%8C%96%E5%8A%A0AI.md)

**6.** 小红书内容创作机器人:**Coze**
- 流程相对单一(主题输入 → 生成内容)
- 需要一键发布
- 创作类应用是 Coze 的舒适区
- 数据隐私要求不高
→ 详见 [场景对照](../05-%E7%AC%AC5%E7%AB%A0-%E5%9F%BA%E4%BA%8E%E4%BD%8E%E4%BB%A3%E7%A0%81%E5%B9%B3%E5%8F%B0%E7%9A%84%E6%99%BA%E8%83%BD%E4%BD%93%E6%90%AD%E5%BB%BA/05-%E4%B8%89%E5%A4%A7%E5%B9%B3%E5%8F%B0%E5%AF%B9%E6%AF%94%E4%B8%8E%E9%80%89%E5%9E%8B.md#-%E7%9C%9F%E5%AE%9E%E5%9C%BA%E6%99%AF%E5%BA%94%E7%94%A8%E5%AF%B9%E7%85%A7)

**7.** 企业内部 AI 文档问答 + 流程自动化:**Dify + n8n 组合**
- **Dify** 做 AI 文档问答(RAG + 自定义 Agent + 本地部署保数据安全)
- **n8n** 做流程自动化(触发器 + 集成内部系统)
- 真实企业级方案常常**多平台组合**
→ 详见 [选型决策树](../05-%E7%AC%AC5%E7%AB%A0-%E5%9F%BA%E4%BA%8E%E4%BD%8E%E4%BB%A3%E7%A0%81%E5%B9%B3%E5%8F%B0%E7%9A%84%E6%99%BA%E8%83%BD%E4%BD%93%E6%90%AD%E5%BB%BA/05-%E4%B8%89%E5%A4%A7%E5%B9%B3%E5%8F%B0%E5%AF%B9%E6%AF%94%E4%B8%8E%E9%80%89%E5%9E%8B.md#-%E7%BB%88%E6%9E%81%E9%80%89%E5%9E%8B%E5%86%B3%E7%AD%96%E6%A0%91)

## 第 6 章 框架开发实践

→ 来自 [第 6 章总览](../06-%E7%AC%AC6%E7%AB%A0-%E6%A1%86%E6%9E%B6%E5%BC%80%E5%8F%91%E5%AE%9E%E8%B7%B5/00-%E7%AB%A0%E8%8A%82%E6%80%BB%E8%A7%88.md)

### 题目

1. 框架的本质是什么?它给开发者带来哪 4 大价值?
2. AutoGen 的核心哲学是"对话驱动协作"。它的 3 大核心组件分别是什么?各自职责?
3. AutoGen 的 `RoundRobinGroupChat` 适合什么场景?局限是什么?
4. AgentScope 选择"消息驱动"架构而非"对话驱动",带来了哪 4 大优势?
5. AgentScope 用 Pydantic 数据模型做"结构化输出"的目的是什么?在狼人杀案例里如何应用?
6. CAMEL 的"Inception Prompting"包含哪 4 个关键部分?为什么最后一项(行为约束)最重要?
7. CAMEL 为什么只设计 2 个 Agent?这是限制还是设计?
8. LangGraph 相比 LangChain 解决了什么核心问题?
9. LangGraph 的 3 大核心概念是什么?为什么它"天然适合 Reflection"?
10. 你要做一个"代码自动修复 Agent"(写代码 → 跑测试 → 失败就改 → 通过为止),选哪个框架?为什么?

<details>
<summary>👉 参考答案(点开)</summary>

**1.** 框架 = **经过验证的"规范"**,把所有 Agent 共有的、重复性的工作抽象封装。
4 大价值:
- **代码复用 + 开发效率**(主循环不用自己写)
- **核心组件解耦 + 可扩展**(Model/Tool/Memory 分层)
- **标准化复杂状态管理**(上下文窗口/历史/多轮)
- **可观测性 + 调试**(回调机制 + 事件埋点)
→ 详见 [框架本质](../06-%E7%AC%AC6%E7%AB%A0-%E6%A1%86%E6%9E%B6%E5%BC%80%E5%8F%91%E5%AE%9E%E8%B7%B5/01-%E4%B8%BA%E4%BB%80%E4%B9%88%E9%9C%80%E8%A6%81%E6%A1%86%E6%9E%B6.md#-611-%E6%A1%86%E6%9E%B6%E7%9A%84%E6%9C%AC%E8%B4%A8%E7%BB%8F%E8%BF%87%E9%AA%8C%E8%AF%81%E7%9A%84%E8%A7%84%E8%8C%83)

**2.** AutoGen 3 大组件:
- **AssistantAgent**:任务主要解决者,封装 LLM,通过 system_message 定义专家角色
- **UserProxyAgent**:双重角色 —— 代表用户发起任务 + 执行代码/工具
- **Team**(如 RoundRobinGroupChat):协调多 Agent 协作
→ 详见 [核心组件](../06-%E7%AC%AC6%E7%AB%A0-%E6%A1%86%E6%9E%B6%E5%BC%80%E5%8F%91%E5%AE%9E%E8%B7%B5/02-AutoGen-%E5%AF%B9%E8%AF%9D%E9%A9%B1%E5%8A%A8.md#-622-%E6%A0%B8%E5%BF%83%E6%99%BA%E8%83%BD%E4%BD%93%E7%BB%84%E4%BB%B6)

**3.** `RoundRobinGroupChat` 适合**流程相对固定**的任务(如软件开发:PM → Eng → Reviewer → User)。
局限:
- **流程僵化** —— 不适合非线性任务
- **不灵活** —— 中途要换路径很难
- LLM 不确定性 → 可能产生偏离预期回复
→ 详见 [优劣](../06-%E7%AC%AC6%E7%AB%A0-%E6%A1%86%E6%9E%B6%E5%BC%80%E5%8F%91%E5%AE%9E%E8%B7%B5/02-AutoGen-%E5%AF%B9%E8%AF%9D%E9%A9%B1%E5%8A%A8.md#-625-autogen-%E7%9A%84%E4%BC%98%E5%8A%BF%E4%B8%8E%E5%B1%80%E9%99%90)

**4.** AgentScope 消息驱动 4 大优势:
- **异步解耦**(发送方/接收方不等待 → 高并发)
- **位置透明**(本地/远程 Agent 都一样调 → 可分布式)
- **可观测性**(每条消息可记录追踪)
- **可靠性**(消息持久化 + 重试 → 容错)
→ 详见 [消息驱动](../06-%E7%AC%AC6%E7%AB%A0-%E6%A1%86%E6%9E%B6%E5%BC%80%E5%8F%91%E5%AE%9E%E8%B7%B5/03-AgentScope-%E6%B6%88%E6%81%AF%E9%A9%B1%E5%8A%A8.md#-632-%E6%B6%88%E6%81%AF%E9%A9%B1%E5%8A%A8%E6%9E%B6%E6%9E%84%E6%A0%B8%E5%BF%83%E5%88%9B%E6%96%B0)

**5.** Pydantic 结构化输出的目的:**用代码层面的约束自动执行游戏规则**。
狼人杀案例应用:
- 女巫的 `WitchActionModelCN`:必须明确"用解药 or 用毒药",**字段定义就禁止了一晚同时用两种**
- 投票模型:**强制玩家名字必须在存活列表内**
- 这样不用代码层面再写一堆 if-else 验证
→ 详见 [结构化输出](../06-%E7%AC%AC6%E7%AB%A0-%E6%A1%86%E6%9E%B6%E5%BC%80%E5%8F%91%E5%AE%9E%E8%B7%B5/03-AgentScope-%E6%B6%88%E6%81%AF%E9%A9%B1%E5%8A%A8.md#-%E5%85%B3%E9%94%AE%E8%AE%BE%E8%AE%A1-2%E7%BB%93%E6%9E%84%E5%8C%96%E8%BE%93%E5%87%BA%E7%BA%A6%E6%9D%9F%E8%A7%84%E5%88%99)

**6.** Inception Prompting 4 部分:
- 明确自身角色("你是资深股票交易员...")
- 告知协作者角色("你正在与优秀的 Python 程序员合作...")
- 定义共同目标("你们的共同目标是开发股票分析工具...")
- **行为约束 + 沟通协议**("AI User 一次只提一个步骤"/"用 `<SOLUTION>` 标识完成")
**第 4 项最重要**:保证对话**不偏不乱**,以**高度结构化、任务驱动**的方式推进,没有这个 AI 很容易跑偏。
→ 详见 [引导性提示](../06-%E7%AC%AC6%E7%AB%A0-%E6%A1%86%E6%9E%B6%E5%BC%80%E5%8F%91%E5%AE%9E%E8%B7%B5/04-CAMEL-%E8%A7%92%E8%89%B2%E6%89%AE%E6%BC%94.md#%E6%A6%82%E5%BF%B5-2%E5%BC%95%E5%AF%BC%E6%80%A7%E6%8F%90%E7%A4%BAinception-prompting)

**7.** CAMEL 只设计 2 个 Agent 是**设计而非限制**。
原因:
- **极简哲学** —— "少即是多"
- 2 个跨领域专家结对**最接近真实工作场景**
- 设计复杂度最低,**易研究和复现**
- 学术研究目的是探索"最少干预下的自主协作"
**代价**:复杂多 Agent 协作要用 AutoGen / AgentScope。
→ 详见 [独特价值](../06-%E7%AC%AC6%E7%AB%A0-%E6%A1%86%E6%9E%B6%E5%BC%80%E5%8F%91%E5%AE%9E%E8%B7%B5/04-CAMEL-%E8%A7%92%E8%89%B2%E6%89%AE%E6%BC%94.md#-646-camel-%E7%9A%84%E7%8B%AC%E7%89%B9%E4%BB%B7%E5%80%BC)

**8.** LangGraph 解决的核心问题:**LangChain 的链式结构只能单向流动,无法处理循环/分支/回溯**。
LangGraph 把流程建模为**图(State Graph)**:
- 节点(Node)= 操作
- 边(Edge)= 跳转逻辑
- 天然支持循环 → Reflection 完美适配
→ 详见 [核心理念](../06-%E7%AC%AC6%E7%AB%A0-%E6%A1%86%E6%9E%B6%E5%BC%80%E5%8F%91%E5%AE%9E%E8%B7%B5/05-LangGraph-%E5%9B%BE%E9%A9%B1%E5%8A%A8.md#-651-langgraph-%E7%9A%84%E6%A0%B8%E5%BF%83%E7%90%86%E5%BF%B5)

**9.** LangGraph 3 大概念:
- **节点 (Node)**:每一步操作(LLM/工具/数据处理)
- **边 (Edge)**:节点间跳转逻辑(普通边 / 条件边)
- **状态 (State)**:在节点间流动的数据载体(TypedDict)
**为啥适合 Reflection**:Reflection = 执行 → 反思 → 修订循环,LangGraph 用**一个条件边**就能表达:
```python
graph.add_conditional_edges(
    "critic",
    lambda s: "execute" if s["needs_revision"] else "end",
    {"execute": "execute_node", "end": END}
)
```
而第 4 章手撕版要写 for 循环 + 早停判断。
→ 详见 [杀手锏应用](../06-%E7%AC%AC6%E7%AB%A0-%E6%A1%86%E6%9E%B6%E5%BC%80%E5%8F%91%E5%AE%9E%E8%B7%B5/05-LangGraph-%E5%9B%BE%E9%A9%B1%E5%8A%A8.md#-langgraph-%E7%9A%84%E6%9D%80%E6%89%8B%E9%94%8F%E5%BA%94%E7%94%A8)

**10.** 代码自动修复 Agent:**LangGraph**
- 任务本质是"**写代码 → 跑 → 失败再改**" → **典型的循环**
- LangGraph 用一条条件边就表达
- 可加 Reflection(反思失败原因)
- 可加 checkpointer(持久化中间状态)
- 备选:**AutoGen 用 UserProxy(执行代码) + Engineer 也可以**,但循环逻辑不如 LangGraph 直观
→ 详见 [场景对照](../06-%E7%AC%AC6%E7%AB%A0-%E6%A1%86%E6%9E%B6%E5%BC%80%E5%8F%91%E5%AE%9E%E8%B7%B5/06-%E5%9B%9B%E5%A4%A7%E6%A1%86%E6%9E%B6%E5%AF%B9%E6%AF%94.md#-%E7%9C%9F%E5%AE%9E%E5%9C%BA%E6%99%AF%E5%BA%94%E7%94%A8%E5%AF%B9%E7%85%A7)

</details>

## 第 7 章 构建你的智能体框架

→ 来自 [第 7 章总览](../07-%E7%AC%AC7%E7%AB%A0-%E6%9E%84%E5%BB%BA%E4%BD%A0%E7%9A%84%E6%99%BA%E8%83%BD%E4%BD%93%E6%A1%86%E6%9E%B6/00-%E7%AB%A0%E8%8A%82%E6%80%BB%E8%A7%88.md)

### 题目

1. 为什么要自建框架?它带来的 3 大价值是什么?
2. HelloAgents 的 4 大设计理念是什么?哪一个最特别?
3. HelloAgents 的"万物皆为工具"哲学是什么意思?和其他框架比有什么优势?
4. `provider="auto"` 的自动检测机制是怎么工作的?优先级是怎样的?
5. 不修改 hello-agents 源码,如何扩展支持一个新的 LLM 提供商?
6. Agent 抽象基类用 `ABC + @abstractmethod` 强制约束什么?为什么这种设计好?
7. `BaseTool` 类的 `description` 字段为什么至关重要?
8. ToolRegistry 的 `get_openai_tools_schema()` 方法的作用是什么?

<details>
<summary>👉 参考答案(点开)</summary>

**1.** 自建框架的 3 大价值:
- **深度理解 Agent 工作原理**(亲手实现每个组件)
- **获得完全控制权**(根据需求精确调优)
- **培养系统设计能力**(模块化/接口/错误处理)
另外:**避免市面框架的局限性**(过度抽象/快速迭代/黑盒/依赖复杂)。
→ 详见 [01-为什么自建框架](../07-%E7%AC%AC7%E7%AB%A0-%E6%9E%84%E5%BB%BA%E4%BD%A0%E7%9A%84%E6%99%BA%E8%83%BD%E4%BD%93%E6%A1%86%E6%9E%B6/01-%E4%B8%BA%E4%BB%80%E4%B9%88%E8%87%AA%E5%BB%BA%E6%A1%86%E6%9E%B6.md)

**2.** HelloAgents 4 大设计理念:
- 轻量级 + 教学友好
- 基于标准 API(OpenAI 兼容)
- 渐进式学习路径(每章一个 pip 版本)
- **万物皆为工具**(最特别,极致简化心智模型)
→ 详见 [4 大理念](../07-%E7%AC%AC7%E7%AB%A0-%E6%9E%84%E5%BB%BA%E4%BD%A0%E7%9A%84%E6%99%BA%E8%83%BD%E4%BD%93%E6%A1%86%E6%9E%B6/01-%E4%B8%BA%E4%BB%80%E4%B9%88%E8%87%AA%E5%BB%BA%E6%A1%86%E6%9E%B6.md#-712-helloagents-%E7%9A%84-4-%E5%A4%A7%E8%AE%BE%E8%AE%A1%E7%90%86%E5%BF%B5)

**3.** "万物皆为工具":
- 其他框架:Memory/RAG/RL/MCP 都是独立模块,要学多个抽象层
- HelloAgents:**这些都是 Tool**,只需理解 Agent + Tools 两个概念
**优势**:**心智模型最简**,**学习者更容易上手**,**统一接口扩展性强**。
→ 详见 [万物皆为工具](../07-%E7%AC%AC7%E7%AB%A0-%E6%9E%84%E5%BB%BA%E4%BD%A0%E7%9A%84%E6%99%BA%E8%83%BD%E4%BD%93%E6%A1%86%E6%9E%B6/01-%E4%B8%BA%E4%BB%80%E4%B9%88%E8%87%AA%E5%BB%BA%E6%A1%86%E6%9E%B6.md#%E7%90%86%E5%BF%B5-4%E4%B8%87%E7%89%A9%E7%9A%86%E4%B8%BA%E5%B7%A5%E5%85%B7%E6%A0%B8%E5%BF%83%E7%AE%80%E5%8C%96)

**4.** 自动检测 3 级优先:
1. **最高优先级**:特定服务商的环境变量(`MODELSCOPE_API_KEY` / `OPENAI_API_KEY` / `ZHIPU_API_KEY`)
2. **次高**:根据 `base_url`(URL 中的域名 / 端口)
3. **辅助**:API Key 格式(如 `ms-` 前缀 = ModelScope)
→ 详见 [自动检测](../07-%E7%AC%AC7%E7%AB%A0-%E6%9E%84%E5%BB%BA%E4%BD%A0%E7%9A%84%E6%99%BA%E8%83%BD%E4%BD%93%E6%A1%86%E6%9E%B6/02-LLM%E7%BB%9F%E4%B8%80%E6%8E%A5%E5%8F%A3.md#-725-%E8%87%AA%E5%8A%A8%E6%A3%80%E6%B5%8B%E6%9C%BA%E5%88%B6%E6%A0%B8%E5%BF%83%E7%AE%97%E6%B3%95)

**5.** 扩展新 LLM 提供商的正确方式:**继承 + 重写**(不改源码):
```python
class MyLLM(HelloAgentsLLM):
    def __init__(self, provider=None, **kwargs):
        if provider == "your_new_provider":
            # 自定义初始化逻辑
            ...
        else:
            super().__init__(provider=provider, **kwargs)
```
**好处**:不改源码 → 升级 hello-agents 库不会丢失自定义,体现"开闭原则"。
→ 详见 [不改源码扩展](../07-%E7%AC%AC7%E7%AB%A0-%E6%9E%84%E5%BB%BA%E4%BD%A0%E7%9A%84%E6%99%BA%E8%83%BD%E4%BD%93%E6%A1%86%E6%9E%B6/02-LLM%E7%BB%9F%E4%B8%80%E6%8E%A5%E5%8F%A3.md#-723-%E4%B8%8D%E4%BF%AE%E6%94%B9%E6%BA%90%E7%A0%81%E6%89%A9%E5%B1%95%E6%96%B0%E6%8F%90%E4%BE%9B%E5%95%86%E7%BB%A7%E6%89%BF)

**6.** `ABC + @abstractmethod` 强制约束:
- 子类**必须**实现 `run` 方法,**统一调用方式**
- 不实现 → Python 报错,**编译期发现问题**
**好处**:
- **接口稳定**(`run(input_text) -> str`)
- **学一个会一片**(所有 Agent 同样的 API)
- **强制规范**(避免子类设计跑偏)
→ 详见 [[../07-第7章-构建你的智能体框架/03-框架核心接口#🔑 1. **`ABC` + `@abstractmethod` = 抽象类**|抽象类]]

**7.** `description` 至关重要因为:
- **LLM 完全靠 description 决定何时调用工具**
- description 写不好 → 工具调不上 / 乱调
- 是 Tool 设计的**灵魂**
所以写 description 要:**清晰** + **具体** + **说明参数**。
→ 详见 [[../07-第7章-构建你的智能体框架/05-工具系统#🔑 1. **`name` + `description`**|name + description]]

**8.** `get_openai_tools_schema()` 的作用:**把 HelloAgents 内部的 Tool 转换成 OpenAI Function Calling 的 JSON schema**。
意义:**对接 OpenAI 标准**,让 HelloAgents 的 Tool 能直接用于:
- OpenAI Function Calling
- Claude 的工具调用
- 任何支持 OpenAI 标准的 LLM
→ "**内部用自己的格式,外部对接标准**" —— 桥接设计。
→ 详见 [[../07-第7章-构建你的智能体框架/05-工具系统#🔑 3. **`get_openai_schema()` 桥接 Function Calling**|get_openai_schema]]

</details>

## 第 8 章 记忆与检索

→ 来自 [第 8 章总览](../08-%E7%AC%AC8%E7%AB%A0-%E8%AE%B0%E5%BF%86%E4%B8%8E%E6%A3%80%E7%B4%A2/00-%E7%AB%A0%E8%8A%82%E6%80%BB%E8%A7%88.md)

### 题目

1. LLM 的 2 大根本局限是什么?Memory 和 RAG 分别解决哪个?
2. HelloAgents 的 4 种记忆类型分别对应人类记忆的什么层次?
3. WorkingMemory 为什么用纯内存存储而不用数据库?
4. SemanticMemory 用 Qdrant + Neo4j 双数据库,这种设计的好处是什么?
5. MemoryTool 的 `forget` 操作支持 3 种策略,分别是什么?为什么需要"遗忘"?
6. `consolidate` 操作模拟人类记忆的什么过程?默认阈值 0.7 的意义?
7. RAG 三代演进:Naive → Advanced → Modular,每代的主要改进是什么?
8. HyDE 检索的"以毒攻毒"思路是什么?为啥它能提升召回率?
9. MQE 和 HyDE 都需要额外调 LLM,在什么场景下值得用?
10. Memory 和 RAG 的本质区别是什么?什么场景需要二者组合?

<details>
<summary>👉 参考答案(点开)</summary>

**1.** LLM 2 大根本局限:
- **对话遗忘**(无状态,每次 API 调用独立)→ **Memory** 解决
- **知识局限**(训练数据有截止 + 缺乏专业领域知识 + 容易幻觉)→ **RAG** 解决
→ 详见 [2 大局限](../08-%E7%AC%AC8%E7%AB%A0-%E8%AE%B0%E5%BF%86%E4%B8%8E%E6%A3%80%E7%B4%A2/01-%E4%BA%BA%E7%B1%BB%E8%AE%B0%E5%BF%86%E7%B3%BB%E7%BB%9F%E5%90%AF%E5%8F%91.md#-812-llm-%E7%9A%84-2-%E5%A4%A7%E6%A0%B9%E6%9C%AC%E5%B1%80%E9%99%90)

**2.** HelloAgents 4 种记忆对应人类:
- **WorkingMemory** → 工作记忆(短期"现在脑子里想的")
- **EpisodicMemory** → 情景记忆(个人经历事件)
- **SemanticMemory** → 语义记忆(抽象知识)
- **PerceptualMemory** → 感觉记忆扩展(多模态:图/音/视频)
→ 详见 [人类记忆 3 层](../08-%E7%AC%AC8%E7%AB%A0-%E8%AE%B0%E5%BF%86%E4%B8%8E%E6%A3%80%E7%B4%A2/01-%E4%BA%BA%E7%B1%BB%E8%AE%B0%E5%BF%86%E7%B3%BB%E7%BB%9F%E5%90%AF%E5%8F%91.md#-811-%E4%BA%BA%E7%B1%BB%E8%AE%B0%E5%BF%86%E7%B3%BB%E7%BB%9F%E7%9A%84%E5%90%AF%E5%8F%91)

**3.** WorkingMemory 用纯内存的原因:
- **访问速度极快**(对话中频繁读写)
- **会话级生命周期**(对话结束自动清理,**不需要持久化**)
- **容量小**(50 条上限,内存够用)
- 配合 **TTL 60 分钟自动过期** + **容量满删除最低优先级** 双重机制
→ 适合"短期临时信息"的场景。
→ 详见 [WorkingMemory](../08-%E7%AC%AC8%E7%AB%A0-%E8%AE%B0%E5%BF%86%E4%B8%8E%E6%A3%80%E7%B4%A2/02-%E8%AE%B0%E5%BF%86%E7%B3%BB%E7%BB%9F%E5%9B%9B%E7%A7%8D%E7%B1%BB%E5%9E%8B.md#%E7%B1%BB%E5%9E%8B-1workingmemory%E5%B7%A5%E4%BD%9C%E8%AE%B0%E5%BF%86)

**4.** SemanticMemory 用双数据库:
- **Qdrant**(向量库):**语义相似度检索** —— 找"相似的知识"
- **Neo4j**(图库):**实体关系推理** —— 找"关联的概念"
**好处**:
- 既能**语义模糊搜**(向量),又能**精确关系查**(图)
- 评分公式融合两者:`(向量 × 0.7 + 图 × 0.3) × 重要性`
- 适合**复杂知识表示**(实体 + 关系 + 推理)
→ 详见 [SemanticMemory](../08-%E7%AC%AC8%E7%AB%A0-%E8%AE%B0%E5%BF%86%E4%B8%8E%E6%A3%80%E7%B4%A2/02-%E8%AE%B0%E5%BF%86%E7%B3%BB%E7%BB%9F%E5%9B%9B%E7%A7%8D%E7%B1%BB%E5%9E%8B.md#%E7%B1%BB%E5%9E%8B-3semanticmemory%E8%AF%AD%E4%B9%89%E8%AE%B0%E5%BF%86--%E6%9C%80%E5%A4%8D%E6%9D%82)

**5.** 3 种遗忘策略:
- **`importance_based`**:删除重要性低于阈值(如 < 0.2)的记忆
- **`time_based`**:删除超过 N 天(如 30 天)的旧记忆
- **`capacity_based`**:容量满时删除最不重要的
**为什么需要遗忘**:
- 防止记忆爆炸(影响检索效率)
- 提高检索精度(过滤无用噪声)
- **贴近人类心智**(选择性遗忘是大脑特性)
→ 详见 [[../08-第8章-记忆与检索/02-记忆系统四种类型#操作 3:**`forget`(遗忘记忆)** —— 最具认知色彩的功能|forget]]

**6.** `consolidate` 模拟人类记忆的**"记忆固化"**(neuroscience: memory consolidation):
- 短期记忆(海马体)→ 长期记忆(大脑皮层)
- HelloAgents:`working → episodic`,`episodic → semantic`
**0.7 阈值的意义**:**只有真正重要的信息才整合**(避免短期琐事污染长期记忆),贴近大脑筛选机制。
→ 详见 [[../08-第8章-记忆与检索/02-记忆系统四种类型#操作 4:**`consolidate`(整合记忆)**|consolidate]]

**7.** RAG 三代演进:
- **Naive RAG**(2020-21):"检索-读取" 简单流程,**关键词匹配**(TF-IDF/BM25),召回率低
- **Advanced RAG**(2022-23):加各种优化 —— **向量检索 + 查询重写 + Rerank + 上下文压缩**
- **Modular RAG**(2024+):模块化 —— **检索/排序/生成/路由 可组合,可循环可分支**,与 Agent 天然契合
→ 趋势:**简单流程 → 复杂可控**。
→ 详见 [RAG 演进](../08-%E7%AC%AC8%E7%AB%A0-%E8%AE%B0%E5%BF%86%E4%B8%8E%E6%A3%80%E7%B4%A2/03-RAG%E5%9F%BA%E7%A1%80%E4%B8%8E%E5%8E%9F%E7%90%86.md#-833-rag-%E4%B8%89%E4%BB%A3%E6%BC%94%E8%BF%9B%E5%8F%B2)

**8.** HyDE(Hypothetical Document Embedding)"以毒攻毒"思路:
- **传统**:用 query 向量去检索(query 短 + 信息少 + 措辞可能和文档差异大)
- **HyDE**:让 LLM 先**生成一段假设性答案**(像文档段落风格),**用假答的向量去检索**
**为啥有效**:
- LLM 编的假答**风格类似文档**
- 向量空间里更**贴近真文档**
- 提升召回率 → 即使假答有错,也能找到真文档
→ 详见 [HyDE](../08-%E7%AC%AC8%E7%AB%A0-%E8%AE%B0%E5%BF%86%E4%B8%8E%E6%A3%80%E7%B4%A2/04-RAG%E6%9E%B6%E6%9E%84%E4%B8%8E%E9%AB%98%E7%BA%A7%E6%A3%80%E7%B4%A2.md#%E7%AD%96%E7%95%A5-3hydehypothetical-document-embedding%E5%81%87%E8%AE%BE%E6%80%A7%E6%96%87%E6%A1%A3%E5%B5%8C%E5%85%A5)

**9.** MQE 和 HyDE 都增加 1-2 次 LLM 调用,**值得用的场景**:
- **召回率优先**(质量 > 成本):企业知识库 / 法律文档 / 医疗
- **查询多样化**:用户提问表达千差万别
- **专业领域**:文档术语和用户口语差异大
**不值得用**:
- 高频简单查询(用缓存)
- 成本敏感(每次都多花钱)
- query 已经和文档措辞接近
→ 详见 [避坑](../08-%E7%AC%AC8%E7%AB%A0-%E8%AE%B0%E5%BF%86%E4%B8%8E%E6%A3%80%E7%B4%A2/04-RAG%E6%9E%B6%E6%9E%84%E4%B8%8E%E9%AB%98%E7%BA%A7%E6%A3%80%E7%B4%A2.md#%EF%B8%8F-%E5%B0%8F%E7%99%BD%E9%81%BF%E5%9D%91)

**10.** Memory vs RAG 本质区别:
| | Memory | RAG |
|---|---|---|
| 存的内容 | **Agent 自己经历的事**(对话/事件/偏好) | **外部知识**(文档/书) |
| 来源 | Agent 自动累积 | 用户/管理员手动上传 |
| 解决 | 对话遗忘 + 个性化 | 知识局限 + 幻觉 |
**需要组合的场景**:**个性化的知识问答**(如:智能助理基于用户偏好回答专业问题)
- 例:用户问"上次我们聊的 Python 项目,我应该用什么框架?"
  - Memory:找上次聊的项目类型
  - RAG:找相关框架的最新文档
  - LLM:综合两者回答
→ 详见 [RAG vs Memory](../08-%E7%AC%AC8%E7%AB%A0-%E8%AE%B0%E5%BF%86%E4%B8%8E%E6%A3%80%E7%B4%A2/03-RAG%E5%9F%BA%E7%A1%80%E4%B8%8E%E5%8E%9F%E7%90%86.md#-836-rag-vs-memory)

</details>

## 第 9 章 上下文工程

→ 来自 [第 9 章总览](../09-%E7%AC%AC9%E7%AB%A0-%E4%B8%8A%E4%B8%8B%E6%96%87%E5%B7%A5%E7%A8%8B/00-%E7%AB%A0%E8%8A%82%E6%80%BB%E8%A7%88.md)

### 题目

1. "上下文工程"和"提示工程"的演进关系是什么?
2. 什么是"上下文腐蚀(Context Rot)"?为什么会发生?
3. 解释"LLM 的注意力预算"概念。它对设计 Agent 有什么启示?
4. 有效上下文的 3 大组件是什么?常见的两极误区分别是什么?
5. 什么是"及时(JIT)上下文"?它相比预加载有什么优势?
6. 长时程任务的 3 大工程手段是什么?分别适合什么场景?
7. GSSC 流水线的 4 个阶段是什么?
8. ContextBuilder 的综合评分公式是什么?为什么不只用相关性?
9. NoteTool 与 MemoryTool 的本质区别是什么?
10. TerminalTool 的 3 道安全防线是什么?为什么 `head/tail` 参数很重要?

<details>
<summary>👉 参考答案(点开)</summary>

**1.** **上下文工程 = 提示工程的自然演进**:
- 提示工程关注"**写好一句话**"(系统提示/句式/措辞)
- 上下文工程关注"**管理整个对话状态**"(系统提示 + 工具 + 历史 + 检索结果 + ...)
- **提示工程 ⊂ 上下文工程**
- 时机:提示工程是设计期,**上下文工程是运行时动态**
→ 详见 [对比](../09-%E7%AC%AC9%E7%AB%A0-%E4%B8%8A%E4%B8%8B%E6%96%87%E5%B7%A5%E7%A8%8B/01-%E4%BB%80%E4%B9%88%E6%98%AF%E4%B8%8A%E4%B8%8B%E6%96%87%E5%B7%A5%E7%A8%8B.md#-%E4%B8%8A%E4%B8%8B%E6%96%87%E5%B7%A5%E7%A8%8B-vs-%E6%8F%90%E7%A4%BA%E5%B7%A5%E7%A8%8B)

**2.** **上下文腐蚀(Context Rot)**:**随着上下文 tokens 增加,LLM 准确回忆信息的能力反而下降**
**原因**:
- Transformer 的 **O(N²)** 注意力机制 → N 大 → 注意力被"拉薄"
- 训练数据中**长序列样本少** → 模型对长上下文经验不足
- "针堆找针"基准证实:100K tokens 时准确率可能只有 60%
→ 详见 [上下文腐蚀](../09-%E7%AC%AC9%E7%AB%A0-%E4%B8%8A%E4%B8%8B%E6%96%87%E5%B7%A5%E7%A8%8B/01-%E4%BB%80%E4%B9%88%E6%98%AF%E4%B8%8A%E4%B8%8B%E6%96%87%E5%B7%A5%E7%A8%8B.md#921-%E8%87%B4%E5%91%BD%E7%8E%B0%E8%B1%A1%E4%B8%8A%E4%B8%8B%E6%96%87%E8%85%90%E8%9A%80context-rot)

**3.** **注意力预算**:LLM 像人类一样有"工作记忆容量",**每多看一个 token 就消耗一点预算**。
**启示**:
- 上下文是**有限资源 + 边际收益递减**
- **不要无脑塞 tokens**,要精挑细选
- **越精越好,不是越长越好**
→ 详见 [注意力预算](../09-%E7%AC%AC9%E7%AB%A0-%E4%B8%8A%E4%B8%8B%E6%96%87%E5%B7%A5%E7%A8%8B/01-%E4%BB%80%E4%B9%88%E6%98%AF%E4%B8%8A%E4%B8%8B%E6%96%87%E5%B7%A5%E7%A8%8B.md#922-%E5%85%B3%E9%94%AE%E6%A6%82%E5%BF%B5%E6%B3%A8%E6%84%8F%E5%8A%9B%E9%A2%84%E7%AE%97)

**4.** 3 大组件 + 两极误区:
- **System Prompt**:
  - ❌ 过度硬编码(if-else 逻辑写一堆,脆弱)
  - ❌ 过于空泛(只有宏观目标,没具体信号)
  - ✅ "刚刚好"(分区组织 + 最小必要信息集)
- **Tools**:
  - ❌ 臃肿工具集(功能边界模糊 → 选哪个都难)
  - ✅ 最小可行工具集(MVTS)
- **Few-shot**:
  - ❌ 把所有边界条件全塞进去
  - ✅ 精挑多样典型的一组
→ 详见 [有效上下文](../09-%E7%AC%AC9%E7%AB%A0-%E4%B8%8A%E4%B8%8B%E6%96%87%E5%B7%A5%E7%A8%8B/01-%E4%BB%80%E4%B9%88%E6%98%AF%E4%B8%8A%E4%B8%8B%E6%96%87%E5%B7%A5%E7%A8%8B.md#-921-%E6%9C%89%E6%95%88%E4%B8%8A%E4%B8%8B%E6%96%87%E7%9A%84%E8%A7%A3%E5%89%96%E5%AD%A6)

**5.** **JIT(Just-in-Time)上下文**:**运行时按需检索**,不预加载所有数据。
**优势**:
- **避免上下文爆炸**
- **运行时精准**(LLM 写针对性查询)
- **元数据自然传达**(目录/命名/时间戳暗示信息)
- **渐进式披露**(像人类一样按层构建理解)
- **类似人类思维**(我们不死记全部信息,用外部索引按需提取)
→ 详见 [两种范式](../09-%E7%AC%AC9%E7%AB%A0-%E4%B8%8A%E4%B8%8B%E6%96%87%E5%B7%A5%E7%A8%8B/01-%E4%BB%80%E4%B9%88%E6%98%AF%E4%B8%8A%E4%B8%8B%E6%96%87%E5%B7%A5%E7%A8%8B.md#-922-%E4%B8%8A%E4%B8%8B%E6%96%87%E6%A3%80%E7%B4%A2%E7%9A%84%E4%B8%A4%E7%A7%8D%E8%8C%83%E5%BC%8F)

**6.** 长时程 3 大手段:
- **压缩整合(Compaction)**:对话接近上限时**高保真总结** → 适合长对话连续性
- **结构化笔记(Structured Note-taking)**:**写入持久存储** → 适合有里程碑的迭代任务
- **子代理架构(Sub-agent)**:子代理在干净窗口探索后回传摘要 → 适合复杂研究分析
**3 者可组合使用**。
→ 详见 [3 大手段](../09-%E7%AC%AC9%E7%AB%A0-%E4%B8%8A%E4%B8%8B%E6%96%87%E5%B7%A5%E7%A8%8B/01-%E4%BB%80%E4%B9%88%E6%98%AF%E4%B8%8A%E4%B8%8B%E6%96%87%E5%B7%A5%E7%A8%8B.md#-923-%E9%9D%A2%E5%90%91%E9%95%BF%E6%97%B6%E7%A8%8B%E4%BB%BB%E5%8A%A1%E7%9A%84-3-%E5%A4%A7%E6%89%8B%E6%AE%B5)

**7.** GSSC 4 阶段:
- **G - Gather(汇集)**:从 Memory/RAG/历史/自定义 多源汇集候选信息
- **S - Select(选择)**:按"相关性 × 0.7 + 新近性 × 0.3"评分,贪心填充 token 预算
- **S - Structure(结构化)**:组织成 [Role]/[Task]/[Evidence]/[Context]/[Output] 5 分区
- **C - Compress(兜底压缩)**:超限时分区压缩 + 截断标记
→ 详见 [GSSC 流水线](../09-%E7%AC%AC9%E7%AB%A0-%E4%B8%8A%E4%B8%8B%E6%96%87%E5%B7%A5%E7%A8%8B/02-ContextBuilder%E4%B8%8EGSSC.md#-932-gssc-%E6%B5%81%E6%B0%B4%E7%BA%BF%E6%80%BB%E8%A7%88)

**8.** 综合评分公式:
$$\text{score} = \text{relevance\_weight} \times \text{relevance} + \text{recency\_weight} \times \text{recency}$$
默认值:**`0.7 × 相关性 + 0.3 × 新近性`**

**为什么不只用相关性**:
- 旧的虽然相关也可能过时(新近性反映"时效")
- 新的可能不那么相关但需要(对话连续性)
- **结合两者更贴近人类记忆特点**(语义相关 + 时间近因)
→ 详见 [Select 评分](../09-%E7%AC%AC9%E7%AB%A0-%E4%B8%8A%E4%B8%8B%E6%96%87%E5%B7%A5%E7%A8%8B/02-ContextBuilder%E4%B8%8EGSSC.md#-935-%E9%98%B6%E6%AE%B5-2select%E6%99%BA%E8%83%BD%E9%80%89%E6%8B%A9--%E6%A0%B8%E5%BF%83)

**9.** NoteTool vs MemoryTool 本质区别:
| | **MemoryTool** | **NoteTool** |
|---|---|---|
| 关注点 | **对话式记忆**(短期/情景/语义) | **项目式记录**(长期追踪) |
| 存储 | Qdrant + SQLite + Neo4j(数据库) | **Markdown + YAML 文件** |
| 可读性 | 机器友好 | **人机双友好** |
| 版本控制 | 难 | ✅ **Git 友好** |
| 典型用途 | 对话历史 / 用户偏好 | TODO / 项目状态 / 阻塞 |
**互补不替代**:**MemoryTool 是大脑,NoteTool 是笔记本**。
→ 详见 [NoteTool vs MemoryTool](../09-%E7%AC%AC9%E7%AB%A0-%E4%B8%8A%E4%B8%8B%E6%96%87%E5%B7%A5%E7%A8%8B/03-NoteTool%E7%BB%93%E6%9E%84%E5%8C%96%E7%AC%94%E8%AE%B0.md#-941-%E4%B8%BA%E4%BB%80%E4%B9%88%E9%9C%80%E8%A6%81-notetool)

**10.** TerminalTool 3 道安全防线:
- **防线 1: 工作目录限制** —— Agent 只能在指定 workspace 操作,**不能逃出沙盒**
- **防线 2: 白名单命令** —— 只允许 read/list/search 类,**禁止 rm/mv/sudo**
- **防线 3: 输出截断** —— 大文件用 head/tail,**防止 token 爆炸**
**head/tail 参数重要性**:
- 大文件直接读 → **整文件塞上下文** → token 爆炸 → 钱包流血
- 用 `head=50` 或 `tail=100` → **只读关键部分**
- 配合"**渐进式探索**"模式(先 head 再 grep 定位)
→ 详见 [安全机制](../09-%E7%AC%AC9%E7%AB%A0-%E4%B8%8A%E4%B8%8B%E6%96%87%E5%B7%A5%E7%A8%8B/04-TerminalTool%E6%96%87%E4%BB%B6%E8%AE%BF%E9%97%AE.md#-952-%E8%AE%BE%E8%AE%A1%E7%90%86%E5%BF%B5%E4%B8%8E%E5%AE%89%E5%85%A8%E6%9C%BA%E5%88%B6)

</details>

## 第 10 章 智能体通信协议

→ 来自 [第 10 章总览](../10-%E7%AC%AC10%E7%AB%A0-%E6%99%BA%E8%83%BD%E4%BD%93%E9%80%9A%E4%BF%A1%E5%8D%8F%E8%AE%AE/00-%E7%AB%A0%E8%8A%82%E6%80%BB%E8%A7%88.md)

### 题目

1. 单体 Agent 有哪 3 大限制?通信协议如何解决?
2. MCP / A2A / ANP 三大协议分别解决什么核心问题?
3. MCP 的三层架构是什么?各层职责是什么?
4. MCP 的 3 大核心能力是什么?各自的性质有什么不同?
5. MCP 与 Function Calling 是替代关系还是互补关系?为什么?
6. 什么是 MCPTool 的"自动展开"机制?多服务器时如何避免冲突?
7. A2A 的核心抽象 Task + Artifact 与 MCP 有什么本质区别?
8. ANP 解决的核心问题是什么?三协议层次关系如何?
9. 写自定义 MCP 服务器时,函数的 docstring 为什么重要?
10. 当下要做"多 Agent 协作"项目,你会用 A2A 协议还是 AutoGen/CrewAI 框架?为什么?

<details>
<summary>👉 参考答案(点开)</summary>

**1.** 单体 Agent 3 大限制:
- **工具集成困境**:每个服务都要写适配器(HTTP/认证/错误处理),不可复用
- **能力扩展瓶颈**:被预定义工具集限制,无法动态发现新服务
- **协作缺失**:多 Agent 协作只能手动编排
**协议如何解决**:
- 标准化接口 → 统一服务访问方式
- 互操作性 → 不同开发者工具可无缝集成
- 动态发现 → 运行时找到新服务
- 可扩展 → 轻松加新功能
→ 详见 [3 大限制](../10-%E7%AC%AC10%E7%AB%A0-%E6%99%BA%E8%83%BD%E4%BD%93%E9%80%9A%E4%BF%A1%E5%8D%8F%E8%AE%AE/01-%E4%B8%BA%E4%BB%80%E4%B9%88%E9%9C%80%E8%A6%81%E9%80%9A%E4%BF%A1%E5%8D%8F%E8%AE%AE.md#-1011-%E5%8D%95%E4%BD%93-agent-%E7%9A%84-3-%E5%A4%A7%E9%99%90%E5%88%B6)

**2.** 三大协议核心问题:
- **MCP** (Anthropic):**Agent ↔ 工具/数据** —— "如何标准化访问外部能力"
- **A2A** (Google):**Agent ↔ Agent** —— "如何让 Agent 互相对话协作"
- **ANP** (社区):**Agent ↔ 网络** —— "如何在大规模网络中发现服务"
→ 详见 [三大协议总览](../10-%E7%AC%AC10%E7%AB%A0-%E6%99%BA%E8%83%BD%E4%BD%93%E9%80%9A%E4%BF%A1%E5%8D%8F%E8%AE%AE/01-%E4%B8%BA%E4%BB%80%E4%B9%88%E9%9C%80%E8%A6%81%E9%80%9A%E4%BF%A1%E5%8D%8F%E8%AE%AE.md#-1013-%E4%B8%89%E5%A4%A7%E5%8D%8F%E8%AE%AE%E6%80%BB%E8%A7%88)

**3.** MCP 三层架构:
- **Host(宿主)**:用户交互界面(如 Claude Desktop) —— 接收提问 + 与 LLM 交互
- **Client(客户端)**:Host 内置,**协议通信** —— 与 MCP Server 建连
- **Server(服务器)**:**具体功能实现** —— 执行实际操作返回结果
**优势**:**关注点分离** —— 开发者只需写 Server,Host/Client 不用管。
→ 详见 [三层架构](../10-%E7%AC%AC10%E7%AB%A0-%E6%99%BA%E8%83%BD%E4%BD%93%E9%80%9A%E4%BF%A1%E5%8D%8F%E8%AE%AE/02-MCP%E5%8D%8F%E8%AE%AE%E8%AF%A6%E8%A7%A3.md#-1021-mcp-%E4%B8%89%E5%B1%82%E6%9E%B6%E6%9E%84)

**4.** MCP 3 大核心能力:
- **Tools(工具)**:**主动** —— 执行操作(调 API/写文件/发邮件)
- **Resources(资源)**:**被动** —— 提供数据(读文件/查库)
- **Prompts(提示)**:**指导性** —— 提供模板(代码审查/报告)
→ 详见 [3 大能力](../10-%E7%AC%AC10%E7%AB%A0-%E6%99%BA%E8%83%BD%E4%BD%93%E9%80%9A%E4%BF%A1%E5%8D%8F%E8%AE%AE/02-MCP%E5%8D%8F%E8%AE%AE%E8%AF%A6%E8%A7%A3.md#-1022-mcp-%E4%B8%89%E5%A4%A7%E6%A0%B8%E5%BF%83%E8%83%BD%E5%8A%9B)

**5.** **互补关系**!
- **Function Calling = LLM 的能力**(决定何时调用 + 生成参数)
- **MCP = 基础设施协议**(工具如何描述 + 如何调用)
- 类比:**Function Calling 是"会打电话"**,**MCP 是"全球电话标准"**
- 实际:Function Calling **使用 MCP 作为通信层**
→ 详见 [MCP vs FC](../10-%E7%AC%AC10%E7%AB%A0-%E6%99%BA%E8%83%BD%E4%BD%93%E9%80%9A%E4%BF%A1%E5%8D%8F%E8%AE%AE/02-MCP%E5%8D%8F%E8%AE%AE%E8%AF%A6%E8%A7%A3.md#-1024-mcp-vs-function-calling)

**6.** MCPTool 自动展开机制:
- 添加 1 个 `MCPTool` 到 Agent 时,**自动连接 Server 发现工具**
- **MCP Server 提供的 N 个工具** → **N 个独立 Tool**注册到 Agent
- 例:`MCPTool(name="calculator")` → 自动展开为 `calculator_add`、`calculator_multiply` 等
**多服务器防冲突**:
- 给每个 MCPTool 不同的 `name` 前缀(如 `fs`、`github`、`db`)
- 展开后变成 `fs_read_file`、`github_search`、`db_query`
→ 详见 [自动展开](../10-%E7%AC%AC10%E7%AB%A0-%E6%99%BA%E8%83%BD%E4%BD%93%E9%80%9A%E4%BF%A1%E5%8D%8F%E8%AE%AE/02-MCP%E5%8D%8F%E8%AE%AE%E8%AF%A6%E8%A7%A3.md#-1027-%E5%9C%A8-agent-%E4%B8%AD%E4%BD%BF%E7%94%A8-mcpmcptool)

**7.** A2A 核心抽象 vs MCP:
| | MCP | A2A |
|---|---|---|
| 核心抽象 | Tools/Resources/Prompts | **Task + Artifact** |
| 性质 | 请求-响应 | **有状态、可追踪的协作单元** |
| 生命周期 | 简单调用 | **创建→协商→代理→执行→完成** |
- **MCP**:适合"**Agent 用工具**"(无状态调用)
- **A2A**:适合"**Agent 间协作**"(有状态任务管理)
→ 详见 [Task + Artifact](../10-%E7%AC%AC10%E7%AB%A0-%E6%99%BA%E8%83%BD%E4%BD%93%E9%80%9A%E4%BF%A1%E5%8D%8F%E8%AE%AE/03-A2A%E5%8D%8F%E8%AE%AE%E5%AE%9E%E6%88%98.md#-1032-%E6%A0%B8%E5%BF%83%E6%8A%BD%E8%B1%A1task--artifact)

**8.** ANP 核心问题:**大规模 Agent 网络中如何发现和路由 Agent**。
三协议层次关系:
```
ANP (找 Agent)       ← 最高层,服务发现
   ↓
A2A (谈协作)         ← 中间层,Agent 通信
   ↓
MCP (用工具)         ← 底层,工具调用
```
完整协议栈:**ANP 找到 → A2A 对话 → MCP 用工具**。
→ 详见 [三协议层次](../10-%E7%AC%AC10%E7%AB%A0-%E6%99%BA%E8%83%BD%E4%BD%93%E9%80%9A%E4%BF%A1%E5%8D%8F%E8%AE%AE/04-ANP%E5%8D%8F%E8%AE%AE%E7%AE%80%E4%BB%8B.md#-1042-%E4%B8%89%E5%8D%8F%E8%AE%AE%E5%B1%82%E6%AC%A1%E5%85%B3%E7%B3%BB)

**9.** Docstring 重要性:
- **LLM 通过 docstring 判断何时调用工具**
- 没写 docstring → 工具 description 为空 → LLM 不知道这工具干啥 → **不会调用**
- 写不好 → LLM 误用 / 乱用
- FastMCP 自动把 **函数 docstring → MCP 工具的 description**
- 同时**类型注解** 自动生成 JSON Schema 参数描述
→ 详见 [关键设计](../10-%E7%AC%AC10%E7%AB%A0-%E6%99%BA%E8%83%BD%E4%BD%93%E9%80%9A%E4%BF%A1%E5%8D%8F%E8%AE%AE/05-%E8%87%AA%E5%AE%9A%E4%B9%89MCP%E6%9C%8D%E5%8A%A1%E5%99%A8%E4%B8%8E%E5%B0%8F%E7%BB%93.md#-1051-%E5%88%9B%E5%BB%BA%E7%AC%AC%E4%B8%80%E4%B8%AA-mcp-%E6%9C%8D%E5%8A%A1%E5%99%A8%E7%94%A8-fastmcp)

**10.** **当下用 AutoGen/CrewAI 框架**,**不用 A2A**。
原因:
- A2A 协议**生态早期**,Python 实现主要为 Sample Code
- AutoGen/AgentScope/CrewAI **生态成熟**,**生产可用**
- 框架解决了多 Agent **编排+对话+状态管理**等工程问题
- A2A 当下**适合学概念**,**生产用框架**
- **未来 A2A 成熟后**,框架可能基于 A2A 实现底层通信(类似 React 用 HTTP)
→ 详见 [A2A vs 框架](../10-%E7%AC%AC10%E7%AB%A0-%E6%99%BA%E8%83%BD%E4%BD%93%E9%80%9A%E4%BF%A1%E5%8D%8F%E8%AE%AE/03-A2A%E5%8D%8F%E8%AE%AE%E5%AE%9E%E6%88%98.md#-1038-a2a-vs-%E7%AC%AC-6-%E7%AB%A0%E5%A4%9A-agent-%E6%A1%86%E6%9E%B6)

</details>

## 第 11 章 Agentic-RL

→ 来自 [第 11 章总览](../11-%E7%AC%AC11%E7%AB%A0-Agentic-RL/00-%E7%AB%A0%E8%8A%82%E6%80%BB%E8%A7%88.md)

### 题目

1. 为什么 Agent 训练需要 RL?SFT 不够吗?
2. SFT 和 RL 在训练目标上有什么本质区别?
3. GRPO 和 PPO 的核心差异是什么?为什么 Agent RL 更爱 GRPO?
4. Agentic-RL 的"端到端流程"包括哪几步?
5. 奖励函数(Reward Function)在 Agent RL 中为什么是"灵魂"?
6. 训练 Agent 时常用的 3 类奖励信号是什么?
7. SFT 冷启动(cold start)的作用是什么?
8. GRPO 中"组采样"(group sampling)是怎么提升稳定性的?
9. Agentic-RL 训练数据的格式与 SFT 有什么不同?
10. 训练后的 Agent 如何验证"真的变强了"而不是过拟合训练集?

<details>
<summary>👉 参考答案(点开)</summary>

**1.** SFT 只能让 Agent **模仿专家轨迹**,无法**探索新策略**:
- SFT 的天花板 = 训练数据的质量上限
- 没法学到"试错经验"
- Agent 在新场景容易卡死(没见过的工具组合)
- RL 通过**奖励**让 Agent 主动探索 + 总结成功模式
→ 详见 [从 LLM 训练到 Agentic-RL](../11-%E7%AC%AC11%E7%AB%A0-Agentic-RL/01-%E4%BB%8ELLM%E8%AE%AD%E7%BB%83%E5%88%B0Agentic-RL.md)

**2.** 训练目标本质区别:
| | SFT | RL |
|---|---|---|
| 目标 | 最大化训练数据的 likelihood | 最大化期望奖励 E[R] |
| 信号 | "正确答案"(监督) | "好/坏"(奖励) |
| 探索 | 无 | 有 |
| 数据 | 静态(给定) | 动态(生成 + 评估) |

**3.** GRPO vs PPO:
- **PPO**:需要 **Value 模型**(估值网络) + Reward 模型 → 4 个模型 + GPU 显存爆炸
- **GRPO**:**去掉 Value 模型**,改用**组内相对奖励**(同一 prompt 采样 N 个回答,用组内均值做 baseline)
- **结果**:GRPO 显存省 40%,实现简单,对 Agent 多步任务更稳定
→ 详见 [GRPO 训练实战](../11-%E7%AC%AC11%E7%AB%A0-Agentic-RL/04-GRPO%E8%AE%AD%E7%BB%83%E5%AE%9E%E6%88%98.md)

**4.** 端到端流程 5 步:
```
1. 准备数据集(任务 + 标准答案/Judge)
2. SFT 冷启动(给 Agent 基础 trajectory 能力)
3. 设计奖励函数(任务成功? 工具调用对吗? 步数少吗?)
4. GRPO 训练(组采样 + 相对优势)
5. 评估(BFCL/GAIA 验证)
```
→ 详见 [端到端流程](../11-%E7%AC%AC11%E7%AB%A0-Agentic-RL/05-%E7%AB%AF%E5%88%B0%E7%AB%AF%E6%B5%81%E7%A8%8B%E4%B8%8E%E5%B0%8F%E7%BB%93.md)

**5.** 奖励函数是"灵魂"因为:
- Agent **学的就是奖励信号**(reward shape what agents learn)
- 奖励设计错 → Agent 学歪了(reward hacking)
- 例:只给"完成任务"奖励 → Agent 可能学会"走捷径"绕过工具调用
→ 详见 [奖励函数设计](../11-%E7%AC%AC11%E7%AB%A0-Agentic-RL/02-%E6%95%B0%E6%8D%AE%E9%9B%86%E4%B8%8E%E5%A5%96%E5%8A%B1%E5%87%BD%E6%95%B0.md)

**6.** 3 类常用奖励信号:
- **结果奖励 Outcome Reward**:任务最终答案对/错
- **过程奖励 Process Reward**:每步工具调用是否合理
- **效率奖励 Efficiency Reward**:步数少/token 少奖励高
→ 三者通常加权组合

**7.** SFT 冷启动的作用:
- 让 Agent **先会基本格式**(Thought/Action/Observation 循环输出)
- 没冷启动直接 RL → Agent 输出乱码,奖励永远 0,学不到东西
- 类比:**先教孩子说话,再教他做事**

**8.** GRPO 组采样提升稳定性:
- 同一 prompt 采样 N 个回答(如 N=8)
- 用**组内平均奖励**做 baseline → advantage = 单样本奖励 - 组均值
- 好处:**自动归一化**,不需要单独训练 Value 模型,梯度方差小

**9.** Agentic-RL 数据格式 vs SFT:
| | SFT 数据 | RL 数据 |
|---|---|---|
| 单条样本 | (prompt, 完整答案) | (prompt, 任务规格) |
| 答案 | 静态文本 | 训练时动态采样 |
| 奖励 | 无 | 必须有 |
| 形式 | JSONL 一行一答 | 任务 + Evaluator |

**10.** 验证"真变强"方法:
- **训练集外测试**(用 BFCL/GAIA 等基准)
- **未见过的工具组合**测试泛化
- **A/B 对比**(训练前 vs 训练后)
- **多 seed 评估**(避免偶然)
- **人工抽查**(看 trajectory 是否合理)
→ 详见 [端到端流程](../11-%E7%AC%AC11%E7%AB%A0-Agentic-RL/05-%E7%AB%AF%E5%88%B0%E7%AB%AF%E6%B5%81%E7%A8%8B%E4%B8%8E%E5%B0%8F%E7%BB%93.md)

</details>

## 第 12 章 智能体性能评估

→ 来自 [第 12 章总览](../12-%E7%AC%AC12%E7%AB%A0-%E6%99%BA%E8%83%BD%E4%BD%93%E6%80%A7%E8%83%BD%E8%AF%84%E4%BC%B0/00-%E7%AB%A0%E8%8A%82%E6%80%BB%E8%A7%88.md)

### 题目

1. 为什么必须评估 Agent?自己跑两个 demo 看效果不行吗?
2. BFCL 评估什么能力?它的 4 大类别(category)是什么?
3. 什么是 AST 匹配?它和字符串完全匹配有什么本质区别?
4. BFCL 的 5 大评估指标是什么?哪个最重要?
5. GAIA 与 BFCL 的核心区别是什么?为什么 GAIA 难度更高?
6. GAIA 的 3 个难度级别(Level 1/2/3)有什么区别?
7. GAIA 的"准精确匹配"(Quasi Exact Match)是什么?为什么不用普通字符串匹配?
8. LLM Judge 的 4 个评分维度是什么?如何避免评委 bias?
9. Win Rate ≈ 50% 说明什么?远高于 50% 一定是好事吗?
10. 为什么数据生成评估要"三层漏斗"(LLM Judge → Win Rate → 人工)?

<details>
<summary>👉 参考答案(点开)</summary>

**1.** 必须评估的原因:
- **客观衡量能力**(不被"感觉良好"骗)
- **横向对比**(知道和 GPT-4/Claude 差多远)
- **指导优化**(知道哪个模块要改)
- **可发表 / 上榜**(学术 + 商业价值)
- demo 看效果 = "**过拟合直觉**",真实分布下可能崩
→ 详见 [第 12 章总览](../12-%E7%AC%AC12%E7%AB%A0-%E6%99%BA%E8%83%BD%E4%BD%93%E6%80%A7%E8%83%BD%E8%AF%84%E4%BC%B0/00-%E7%AB%A0%E8%8A%82%E6%80%BB%E8%A7%88.md)

**2.** BFCL 评估**工具调用能力**。4 大类别:
- **simple**:单工具单次调用
- **multiple**:多工具选一(有干扰项)
- **parallel**:并行调用多工具
- **irrelevance**:不该调工具时拒绝调用
→ 详见 [BFCL](../12-%E7%AC%AC12%E7%AB%A0-%E6%99%BA%E8%83%BD%E4%BD%93%E6%80%A7%E8%83%BD%E8%AF%84%E4%BC%B0/01-BFCL%E5%B7%A5%E5%85%B7%E8%B0%83%E7%94%A8%E8%AF%84%E4%BC%B0.md)

**3.** AST 匹配 vs 字符串匹配:
- **字符串匹配**:`add(1,2)` ≠ `add(1, 2)`(空格都不行)
- **AST 匹配**:把代码解析成**抽象语法树**,比较结构
  - 参数顺序 / 命名参数 / 空格 / 引号风格 → 都被规范化
  - `add(a=1,b=2)` == `add(1, 2)` == `add(b=2, a=1)`
- 本质:**语义等价**而非**字面等价**
→ 详见 [AST 匹配](../12-%E7%AC%AC12%E7%AB%A0-%E6%99%BA%E8%83%BD%E4%BD%93%E6%80%A7%E8%83%BD%E8%AF%84%E4%BC%B0/01-BFCL%E5%B7%A5%E5%85%B7%E8%B0%83%E7%94%A8%E8%AF%84%E4%BC%B0.md)

**4.** BFCL 5 大指标:
- Accuracy(总体准确率) ← **最常用**
- AST Match Rate(AST 匹配率)
- Category Accuracy(分类别准确率) ← **最能定位短板**
- Weighted Score(加权综合分)
- Error Rate(错误率)
**最重要**:看场景。生产用 **Category Accuracy**(知道在哪个类型上崩),刷榜用 **Weighted Score**。

**5.** GAIA vs BFCL:
| | BFCL | GAIA |
|---|---|---|
| 评什么 | 工具调用 | **通用 AI 能力** |
| 输入 | 文本 | **文本+图+PDF+Excel** |
| 任务 | 单点 | **多步骤多工具** |
| 难度 | 中 | **极高(GPT-4 才 30%+)** |
→ GAIA 难因为**真实世界任务需要综合多种能力**

**6.** GAIA 3 难度级别:
- **Level 1**:简单任务(5 步内,1 个工具)
- **Level 2**:中等任务(5-10 步,2-3 个工具)
- **Level 3**:复杂任务(10+ 步,多个工具 + 多模态)
- 现在 GPT-4 + 工具:L1 约 50%,L2 约 30%,L3 约 10%
→ 详见 [GAIA](../12-%E7%AC%AC12%E7%AB%A0-%E6%99%BA%E8%83%BD%E4%BD%93%E6%80%A7%E8%83%BD%E8%AF%84%E4%BC%B0/02-GAIA%E9%80%9A%E7%94%A8%E8%AF%84%E4%BC%B0.md)

**7.** 准精确匹配:
- 普通字符串匹配:`"42"` ≠ `"42.0"` ≠ `"forty-two"`
- 准精确匹配:**先规范化再比较**
  - 去标点 / 去前后空格 / 小写化
  - 数字归一化(`"42.0"` → `"42"`)
  - 单位移除(`"42°C"` → `"42"`)
- 仍不完美:`"42"` vs `"四十二"` 处理不了 → 这是 GAIA 公认局限
→ 详见 [准精确匹配](../12-%E7%AC%AC12%E7%AB%A0-%E6%99%BA%E8%83%BD%E4%BD%93%E6%80%A7%E8%83%BD%E8%AF%84%E4%BC%B0/02-GAIA%E9%80%9A%E7%94%A8%E8%AF%84%E4%BC%B0.md)

**8.** LLM Judge 4 个维度:
- 正确性 Correctness(逻辑对吗,答案准吗)
- 清晰度 Clarity(表述清楚吗)
- 难度匹配 Difficulty Match(难度合适吗)
- 完整性 Completeness(步骤全吗)
**避免 bias**:
- 用**多个不同 LLM 当评委**(GPT-4 + Claude + Gemini 投票)
- **盲评**(不告诉评委题目来源)
- **加人工抽样验证**
→ 详见 [数据质量评估](../12-%E7%AC%AC12%E7%AB%A0-%E6%99%BA%E8%83%BD%E4%BD%93%E6%80%A7%E8%83%BD%E8%AF%84%E4%BC%B0/03-%E6%95%B0%E6%8D%AE%E7%94%9F%E6%88%90%E8%B4%A8%E9%87%8F%E8%AF%84%E4%BC%B0.md)

**9.** Win Rate ≈ 50%:
- **生成数据质量接近真题** ✅
- 这是**理想结果**(说明 AI 出题已经能与人类持平)
**远高于 50% ≠ 一定好**:
- 可能**评委 bias**(评委更喜欢 AI 的固定句式)
- 可能**真题数据集质量低**(对比基数低)
- 可能**任务太简单**(AI 在简单任务上确实超人)
- 必须用**人工抽查**验证

**10.** 三层漏斗设计:
```
LLM Judge(快/便宜) → 1000 题 → 通过率 80%
       ↓
Win Rate(中等) → 800 题 → Win Rate ≥ 45% → 360 题
       ↓
人工验证(慢/贵) → 抽 10% → 最终 approved
```
- 不能只用 LLM Judge:有 bias 风险
- 不能只用人工:成本太高
- 三层组合:**速度 / 成本 / 准确性** 三方平衡
→ 详见 [数据质量评估](../12-%E7%AC%AC12%E7%AB%A0-%E6%99%BA%E8%83%BD%E4%BD%93%E6%80%A7%E8%83%BD%E8%AF%84%E4%BC%B0/03-%E6%95%B0%E6%8D%AE%E7%94%9F%E6%88%90%E8%B4%A8%E9%87%8F%E8%AF%84%E4%BC%B0.md)

</details>

## 🎬 故事比喻:开卷考 vs 闭卷考

| | 闭卷考(纯 LLM) | 开卷考(RAG) |
|---|---|---|
| 你被问"宋朝有多少皇帝" | **凭记忆答**(可能错) | **翻教科书后答**(准) |
| Agent | 容易**幻觉** | 答案**可追溯** |
| 知识更新 | 重训才能更新 | **换教科书即可** |

→ **RAG = 让 LLM 开卷考**。

---

## 📚 8.3.1 什么是 RAG?

> **RAG**(**R**etrieval-**A**ugmented **G**eneration,检索增强生成)
> 在生成回答**之前**,先从外部知识库**检索相关信息**,
> 然后把检索结果作为**上下文**喂给 LLM 生成回答。

### 拆解 3 个动作

| 动作 | 含义 |
|---|---|
| **检索**(Retrieval) | 从知识库查询相关内容 |
| **增强**(Augmented) | 把检索结果融入 prompt |
| **生成**(Generation) | 输出兼具**准确性 + 透明度**的答案 |

## 🔄 8.3.2 RAG 基本工作流程

### 2 大核心环节

```
┌─────────────────────────────────────────────────┐
│      环节 A: 数据准备(一次性)                     │
│                                                   │
│   外部知识 → 数据提取 → 文本分割 → 向量化 → 存入库 │
│                                                   │
└─────────────────────────────────────────────────┘

┌─────────────────────────────────────────────────┐
│      环节 B: 应用阶段(每次问答)                   │
│                                                   │
│   用户问题                                         │
│      ↓                                            │
│   向量化 → 检索相关文档 → 注入 Prompt → LLM 生成   │
│                                                   │
└─────────────────────────────────────────────────┘
```

### 详细流程图

```
                 用户提问
                    │
                    ▼
            ┌──────────────┐
            │  问题向量化     │  ← Embedding 模型
            └──────┬───────┘
                    │
                    ▼
            ┌──────────────┐
            │  向量库检索     │  ← Top-K 相关文档
            └──────┬───────┘
                    │
                    ▼
       ┌──────────────────────┐
       │  构建增强 Prompt:      │
       │  - 用户问题             │
       │  - 检索到的文档(上下文)  │
       │  - 指令(基于上下文答)   │
       └──────────┬───────────┘
                    │
                    ▼
              ┌──────────┐
              │   LLM     │
              └────┬─────┘
                    │
                    ▼
              最终回答(可追溯)
```

## 📖 8.3.3 RAG 三代演进史

### 第一代:**Naive RAG**(2020-2021)朴素 RAG

```
检索-读取(Retrieve-Read)
   ↓
关键词匹配(TF-IDF / BM25)
   ↓
直接拼到 prompt → LLM 生成
```

**特点**:
- ✅ 简单直接
- ❌ 召回率低
- ❌ 关键词无法理解语义

→ 类似第 4 章手撕版,但用关键词检索。

### 第二代:**Advanced RAG**(2022-2023)进阶 RAG

```
预处理 + 检索 + 后处理
   ↓ 添加优化技巧
- 查询重写(Query Rewrite)
- 向量检索(替代关键词)
- Rerank 重排
- 上下文压缩
- 多路检索 + 融合
```

**特点**:
- ✅ 召回 + 精排显著提升
- ✅ 适合生产
- ❌ 流程相对僵化

### 第三代:**Modular RAG**(2024+)模块化 RAG

```
把 RAG 拆成 可组合的模块
   ↓ 灵活编排
- 检索模块 + 排序模块 + 生成模块 + 路由模块 + ...
- 可循环 / 可分支(类似 LangGraph)
```

**特点**:
- ✅ 极度灵活
- ✅ 可适配复杂场景
- ✅ 与 Agent 框架天然契合

### 第四代(萌芽):**Agentic RAG**

> 让 Agent 自主决定:**是否检索 / 检索几次 / 查哪些库**

→ **第 11 章**(Agentic-RL)的方向。

## 🛠 8.3.4 RAG 三大核心组件

### 组件 1:**Embedding 模型**(向量化)

> 把文本变成稠密向量。

```python
text = "Python 是面向对象的编程语言"
vector = embedding_model.encode(text)
# → [0.12, -0.34, 0.56, ..., 0.78]  (例: 1024 维)
```

**特性**:
- 语义相近的文本 → 向量距离近
- 这是 RAG 检索的"灵魂"

**HelloAgents 内置 3 种**:
| 名称 | 部署 | 适用 |
|---|---|---|
| **DashScopeEmbedding** | 云端(阿里) | 生产首选 |
| **LocalTransformerEmbedding** | 本地 | 数据隐私 |
| **TFIDFEmbedding** | 本地纯算 | **兜底/极简** |

详见 [Happy-LLM Embedding](../../Happy-LLM/07-%E7%AC%AC7%E7%AB%A0-%E5%A4%A7%E6%A8%A1%E5%9E%8B%E5%BA%94%E7%94%A8/02-RAG%E5%8E%9F%E7%90%86%E6%B7%B1%E5%85%A5.md#%E6%A6%82%E5%BF%B5-1embedding%E5%B5%8C%E5%85%A5)。

### 组件 2:**Vector Database**(向量数据库)

> 存储 (文本, 向量) 对,**支持高效相似度搜索**。

**HelloAgents 用 Qdrant**:
- 开源 + 性能强
- 支持命名空间隔离(`namespace="user1_docs"`)
- 云端版免费 1GB

### 组件 3:**Retriever**(检索器)

> 给定 query → 返回 top-k 相关文档。

```python
results = vector_store.search(
    query_vector=query_vec,
    top_k=5,                  # 返回 5 条
    filter={"user_id": "u1"}  # 过滤
)
```

## 🐍 8.3.5 RAG 完整 Prompt 模板(必背)

```python
RAG_PROMPT = """
使用以下上下文回答用户的问题。如果你不知道答案,就说你不知道。
总是使用中文回答。

问题: {question}

可参考的上下文:
···
{context}
···

如果给定的上下文无法让你做出回答,请回答"数据库中没有这个内容,我不知道"。

有用的回答:
"""
```

### 3 个关键设计

| 设计 | 目的 |
|---|---|
| `如果你不知道,就说你不知道` | **防止幻觉** |
| `基于上下文回答` | 让 LLM 严格依据文档 |
| `如果上下文无法回答,明示不知道` | 强化诚实性 |

## 🆚 8.3.6 RAG vs Memory

> 这是初学者最容易**混淆**的两个概念。

| 维度 | **Memory** | **RAG** |
|---|---|---|
| **存的是什么** | Agent **自己经历的事**(对话/事件) | **外部知识**(文档/书) |
| **谁提供的** | Agent 自动累积 | 用户/管理员手动上传 |
| **应用场景** | 多轮对话 / 个性化 | 知识问答 / 客服 / 文档查询 |
| **核心解决** | 对话遗忘 | 知识局限 + 幻觉 |
| **典型存储** | Working/Episodic/Semantic 4 种 | Vector DB |

### 完美组合:**Memory + RAG**

```
用户问: "上次我们聊的 Python 项目,我应该用什么框架?"
   ↓
Agent:
   1. Memory 找上下文 → 用户上次聊的项目类型
   2. RAG 找知识库 → 相关框架的最新文档
   3. LLM 综合回答
```

→ **HelloAgents 用同一个 ToolRegistry 接入两者**,优雅极致。

## ⚠️ 8.3.7 常见踩坑

### 坑 1:**文档分块不当**

```
原文档: 一篇 5000 字论文
   ↓
错误: 切成 50 字 × 100 块 → 缺乏上下文
错误: 切成 5000 字 × 1 块 → 检索粒度太粗
正确: 切成 500 字 × 10 块,**带 100 字重叠**
```

### 坑 2:**Embedding 模型混用**

```
建库时用 bge-m3 (1024 维)
查询时用 OpenAI text-embedding-3 (1536 维)
   ↓
维度不匹配 → 查不到
```

→ **建库 + 查询必须用同一个模型**。

### 坑 3:**Top-K 取太大**

```
top_k=20 → 噪声多,token 浪费,LLM 困惑
top_k=3~5 → 通常最佳
```

### 坑 4:**忘了 Rerank**

```
向量检索可能召回相关性低的
加 Rerank 模型(如 bge-reranker)显著提升精度
```

| **3 代演进** | Naive → Advanced → Modular |

# 1.2 智能体的构成与运行原理

⬅ [01-什么是智能体](01-%E4%BB%80%E4%B9%88%E6%98%AF%E6%99%BA%E8%83%BD%E4%BD%93.md)　|	➡ [03-动手实现旅行助手](03-%E5%8A%A8%E6%89%8B%E5%AE%9E%E7%8E%B0%E6%97%85%E8%A1%8C%E5%8A%A9%E6%89%8B.md)

---

## 🎬 故事比喻：餐厅服务员的一天

想象一个**餐厅服务员**的工作循环：

```
看到客人进门（感知）
   ↓
想：该带他去哪桌？（思考）
   ↓
带他到 5 号桌（行动）
   ↓
客人坐下点单（环境反馈：新的观察）
   ↓
想：该去厨房下单（思考）
   ↓
......（循环继续）
```

→ **Agent 也是这样工作的**。这一节我们看 Agent 怎么"上班"。

---

## 🗺 1.2.1 PEAS 模型：定义任务环境

> 在让 Agent 干活前，先**明确它在哪个环境里干什么**。
> 工具：**PEAS 模型**。

### PEAS 四要素

| 缩写 | 全称 | 含义 |
|---|---|---|
| **P** | **P**erformance | 性能度量（怎么算"干得好"） |
| **E** | **E**nvironment | 环境（智能体在哪干活） |
| **A** | **A**ctuators | 执行器（用什么"手脚"行动） |
| **S** | **S**ensors | 传感器（用什么"眼睛"感知） |

### 例子：智能旅行助手的 PEAS

| 要素         | 内容                             |
| ---------- | ------------------------------ |
| **性能度量 P** | 行程合理 + 用户满意 + 预算达标 + 时效性       |
| **环境 E**   | 互联网（航空公司 API、酒店预订系统、地图服务、天气服务） |
| **执行器 A**  | 调用各种 API、返回行程文本、调起浏览器订票        |
| **传感器 S**  | 用户输入、API 返回数据、网页爬取内容           |

### ⭐ 数字环境的 4 大特性

LLM Agent 所处的环境，有这几个"坑"必须知道：

#### 🅰 **部分可观察**（Partially Observable）
- 旅行助手查航班 → 只能看到 API **返回的部分数据**
- 解法：Agent 必须**有记忆**（记住已查过的）+ **会探索**（试不同日期）

#### 🅱 **随机性**（Stochastic）
- 同一个航班，**两次查询价格可能不同**
- 解法：Agent 必须**处理不确定性**

#### 🅲 **多智能体**（Multi-agent）
- 其他用户、其他自动化脚本、航司的动态调价系统**都是其他 Agent**
- 它们的行为（如抢走最后一张特价票）**直接改变环境**
- 解法：Agent 要**快速响应**

#### 🅳 **序贯且动态**（Sequential & Dynamic）
- **序贯**：当前动作影响未来（订错酒店后果严重）
- **动态**：环境自己也在变（你思考时机票涨价了）
- 解法：循环要**快速灵活**

→ 这四个特性决定了 Agent **必须循环工作 + 实时调整**，不能一锤子买卖。

## 🔁 1.2.2 智能体的运行机制：Agent Loop

> **Agent Loop = 感知 → 思考 → 行动 → 观察 → 感知 → ...**
> 这是 Agent 的"心跳"。

### 完整循环图

```
       ┌─────────────────────────────────────┐
       │                                       │
       ▼                                       │
   ┌────────┐    ┌─────────┐    ┌─────────┐   │
   │ 1.感知  │ ──▶│ 2.思考   │──▶ │ 3.行动   │  │
   │Perception│   │Thought  │   │ Action  │   │
   └────────┘    └─────────┘    └────┬────┘   │
                                       │        │
                                       ▼        │
                              ┌──────────────┐  │
                              │  环境状态变化   │──┘
                              │ 4.新的观察     │
                              └──────────────┘
```

### 4 阶段详解

#### ① 感知（Perception）
- 通过传感器接收**观察（Observation）**
- 可能是用户的初始指令，或上一步行动的结果反馈

#### ② 思考（Thought）⭐ —— Agent 的核心
**LLM 在这里发力**，分两个子步骤：

| 子步骤                      | 干啥                         |
| ------------------------ | -------------------------- |
| **规划**（Planning）         | 基于观察 + 记忆，更新对任务的理解，制定/调整计划 |
| **工具选择**（Tool Selection） | 选最合适的工具 + 确定参数             |

#### ③ 行动（Action）
- 通过执行器执行具体行动
- 通常是**调用工具**（API、代码、搜索引擎）
- 对环境**施加影响**

#### ④ 新的观察（New Observation）
- 行动引起环境变化 → 产生新观察
- 这个新观察**回到第①步**，开始下一轮循环

→ **不断循环**，逐步推进任务，从初始状态 → 目标状态。

## 📡 1.2.3 智能体的感知与行动：T-A-O 范式

> **T-A-O = Thought-Action-Observation**
> 这是 LLM Agent 在工程上**最标准的交互协议**。

### 结构化输出的 3 个核心字段

LLM Agent 每次的输出**不是自由文本**，而是结构化的：

#### 字段 1：Thought（思考）
- 自然语言写的"内部独白"
- 分析当前情况、回顾上一步、规划下一步
- → **AI 的内心戏**

#### 字段 2：Action（行动）
- 决定对环境干什么
- 通常以**函数调用**形式
- → **AI 的执行命令**

#### 字段 3：Observation（观察）
- 行动结果**被处理成自然语言后**反馈给 AI
- → **环境给 AI 的回应**

### 完整例子

```
Thought: 用户想知道北京的天气。我需要调用天气查询工具。
Action: get_weather("北京")
Observation: 北京当前天气为晴，气温 25 摄氏度，微风。
```

→ Agent 看到 Observation 后，进入**下一轮 T-A-O**。

### ⭐ 为什么 Observation 要"翻译"成自然语言？

工具直接返回的可能是 **JSON / XML 等机器格式**：
```json
{"city": "Beijing", "temp_c": 25, "condition": "Sunny", "wind_kph": 12, ...}
```

但 LLM 处理自然语言效率最高，所以**感知系统要把 JSON 翻译成人话**：
```
北京当前天气：晴，气温 25 摄氏度，微风。
```

→ 这就是**感知系统作为"传感器"的核心职责**。

---

## 🎯 T-A-O 范式的工程优势

| 优势      | 解释                       |
| ------- | ------------------------ |
| **可解释** | Thought 写出推理过程，调试方便      |
| **可控**  | Action 是结构化的，能被外部解析器精确执行 |
| **可循环** | Observation 标准化后回流，闭环顺畅  |
| **可扩展** | 加新工具只需注册到工具库             |

这就是为什么 **LangChain、AutoGen、CrewAI** 等框架都用 T-A-O 作为底层协议。

→ 这种"思考-行动"交替的循环就是 **ReAct（Reason + Act）框架**，第 4 章会详讲。

## ⚠️ 小白避坑

1. **PEAS 不是花拳绣腿**
   - 设计 Agent 前**真的要先想清楚 PEAS**，否则做出来跑偏
2. **Observation 必须自然语言化**
   - 直接把 JSON 塞给 LLM 会浪费 token、降低理解
3. **循环要设上限**
   - LLM 可能陷入"思考-行动"死循环
   - 工程上**必须设 max_iterations**（如 5~10）
4. **Action 要严格格式化**
   - 否则解析器无法正确提取
   - 通过 **Function Calling**（OpenAI/Claude 的标准化能力）解决

## 📌 1.2 节要点

| 知识点            | 一句话                                |
| -------------- | ---------------------------------- |
| **PEAS 模型**    | 性能 / 环境 / 执行器 / 传感器                |
| 环境 4 特性        | 部分可观察 + 随机性 + 多智能体 + 序贯动态          |
| **Agent Loop** | 感知 → 思考 → 行动 → 观察                  |
| 思考阶段拆解         | 规划 + 工具选择                          |
| **T-A-O 范式**   | Thought + Action + Observation 三段式 |
| 工程关键           | Observation 必须自然语言化                |

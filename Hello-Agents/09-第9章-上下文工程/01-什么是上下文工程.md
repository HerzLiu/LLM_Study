# 9.1-9.2 什么是上下文工程 + 为什么重要

⬅ [00-章节总览](00-%E7%AB%A0%E8%8A%82%E6%80%BB%E8%A7%88.md)	|	➡ [02-ContextBuilder与GSSC](02-ContextBuilder%E4%B8%8EGSSC.md)

---

## 🎬 故事比喻:从"写好一句话"到"管理一段对话"

```
                上下文工程的演进

        提示工程 (Prompt Engineering)
              ↓ 关注:写好一句话
        系统提示、句式、措辞
                  │
                  ▼
        上下文工程 (Context Engineering)
              ↓ 关注:管理整个对话状态
        系统提示 + 工具 + 外部数据 + 历史 + ...
```

→ **上下文工程是提示工程的自然演进**。

---

## 🎯 9.1 什么是上下文工程?

### 定义

> **上下文(Context)** = 在每次 LLM 调用时,所有进入模型视野的 tokens
> **上下文工程** = **如何在 LLM 的固有约束下,优化这些 tokens 的"效用"**

→ **核心问题**:**什么样的上下文配置,最可能让模型产出我们期望的行为?**

### 上下文包含什么?

```
上下文 = 系统提示
       + 工具定义
       + MCP / 外部数据
       + 消息历史
       + 检索结果 (RAG/Memory)
       + ...
```

→ **不止 prompt,而是 LLM 在某一时刻"看到的一切"**。

---

## 🆚 上下文工程 vs 提示工程

| 维度 | **提示工程** | **上下文工程** |
|---|---|---|
| 关注点 | 写好**一句话** | 管理**整个对话状态** |
| 时机 | 设计期(写好就完事) | **运行时**(动态构建) |
| 颗粒度 | 系统提示 / few-shot | + 工具/记忆/历史/检索 |
| 适用 | 单轮任务 | **长程多轮智能体** |
| 演进关系 | 提示工程 ⊂ 上下文工程 | |

→ **早期 LLM**:提示工程为主(单轮分类/生成)
→ **现在 Agent 时代**:上下文工程更重要(多轮工具调用)

---

## ⚠️ 9.2 为什么上下文工程这么重要?

### 9.2.1 致命现象:**上下文腐蚀(Context Rot)**

> **随着上下文 tokens 增加,LLM 准确回忆信息的能力反而下降**!

#### "针堆找针"(Needle-in-a-Haystack)基准

```
实验:在 100K tokens 的文档中藏一句"关键信息",问 LLM 找出来

结果:
   1K  tokens 上下文 → 准确率 99%
   10K tokens 上下文 → 准确率 95%
   100K tokens 上下文 → **准确率 60%** ⚠️
```

→ **不是"越长越好"**,**长上下文会让 LLM"走神"**。

#### 为什么会有上下文腐蚀?

**Transformer 架构约束**:
- 每个 token 与所有 token 建立关联 → **O(N²) 注意力关系**
- N 越大 → 注意力被"**拉薄**"
- + 训练数据中**长序列样本少** → 模型对长上下文经验不足

→ 这是**架构性问题**,**短期无法根治**。

---

### 9.2.2 关键概念:**"注意力预算"**

> 把 LLM 想象成有限"工作记忆"的人:
> 每多看一个 token,就**消耗一点注意力预算**

```
人类:工作记忆 7±2 个项目
LLM:注意力预算有限(具体取决于模型规模)

→ 不要无脑塞 tokens,要精挑细选
→ 上下文必须被视为"有限资源 + 边际收益递减"
```

---

## 🏗 9.2.1 有效上下文的"解剖学"

> 优秀的上下文工程目标:**用尽可能少、但高信号密度的 tokens,最大化期望结果概率**。

### 3 大核心组件

#### 组件 1:**System Prompt**(系统提示)

**两极误区**(都不可取):

| 误区 | 表现 | 后果 |
|---|---|---|
| ❌ **过度硬编码** | 写一堆 if-else 逻辑 | 维护成本高、易碎 |
| ❌ **过于空泛** | 只给宏观目标 | 缺少具体信号,假定错误共识 |

**正确做法**:**"刚刚好"的高度**
- 分区组织(`<background>`、`<tools>`、`<output>`...)
- 用 XML / Markdown 分隔
- 追求**最小必要信息集**("最小"≠"最短")
- **先用最好的模型 + 最小提示试跑,再按失败模式增补**

#### 组件 2:**Tools**(工具)

**核心原则**:
- **职责单一**,相互低重叠
- **接口语义清晰**,入参描述无歧义
- **对错误鲁棒**
- 返回 **token 友好** 的信息

**致命失败模式**:**"臃肿工具集"**
- 功能边界模糊 → "选哪个工具"本身就难
- **如果人类工程师都说不准,别指望 LLM 做得更好**

**最佳实践**:**最小可行工具集(MVTS)** —— 精挑细选,**少而精**。

#### 组件 3:**Few-shot Examples**(示例)

**原则**:
- **始终推荐**(对 LLM 而言,好示例胜过千言万语)
- ❌ 不要把所有边界条件全塞进去
- ✅ 精挑**多样且典型**的一组(画"期望行为"画像)

→ **总指导思想**:**信息充分但紧致**。

---

## 🔄 9.2.2 上下文检索的两种范式

### 范式 1:**预加载检索**(传统 RAG)

```
推理前一次性 embedding 检索 → 全部相关数据塞进上下文 → LLM 推理
```

**缺点**:
- 数据量大 → 上下文爆炸
- 检索精度受限于"一次提问"

### 范式 2:**及时上下文**(Just-in-Time, JIT)⭐ **新趋势**

```
预先只存"轻量引用"(文件路径/查询语句/URL)
   ↓
运行时按需用工具动态加载
   ↓
LLM 写针对性查询,用 head/tail 等命令分析大数据
```

**优势**(对比 JIT):
- **不预加载**所有相关数据
- **运行时按需**,精准高效
- 文件名/目录/时间戳本身**就传达元信息**

#### 渐进式披露(Progressive Disclosure)

```
Step 1: 看目录 → 知道有哪些文件
Step 2: 看文件大小 → 暗示复杂度
Step 3: 看命名 → 暗示用途
Step 4: 看时间戳 → 暗示相关性
Step 5: 只读关键文件
```

→ **像人类一样**:**按层构建理解,只在工作记忆中保留"当前必要子集"**。

### 混合策略(实战常用)

```
前置加载:少量"高价值"上下文(如 README/项目约定)
   +
运行时探索:按需检索具体文件(glob / grep / TerminalTool)
```

→ 兼顾**速度 + 灵活性**。

## 🎯 9.2.3 面向长时程任务的 3 大手段

> **长时程任务**:大型代码库迁移、跨数小时的系统研究...
> 上下文窗口**再大也不够**,必须用工程手段。

### 手段 1:**压缩整合(Compaction)**

```
定义:接近上下文上限时,对话进行"高保真总结",用摘要重启新窗口
```

**实践**:
- 让 LLM 压缩并保留:**架构决策、未解决缺陷、实现细节**
- 丢弃:**重复工具输出、噪声**
- 新窗口 = 压缩摘要 + 最近少量高相关工件

**调参建议**:
- **先优化召回**(确保不漏关键信息)
- **再优化精度**(剔除冗余)
- "**轻触式压缩**":只清理"深历史中的工具调用与结果"

### 手段 2:**结构化笔记(Structured Note-taking)**

```
定义:Agent 以固定频率把关键信息写入"上下文外的持久存储",后续按需拉回
```

**价值**:
- **极低上下文开销** 维持持久状态
- 例:TODO 列表、`NOTES.md`、关键结论/依赖/阻塞项索引
- **跨数十次工具调用、多轮上下文重置**仍能保持进度

→ **HelloAgents 的 NoteTool 就是干这个**(见 [9.4 节](03-NoteTool%E7%BB%93%E6%9E%84%E5%8C%96%E7%AC%94%E8%AE%B0.md))。

### 手段 3:**子代理架构(Sub-agent Architectures)**

```
主代理:高层规划 + 综合
   │
   ├─ 子代理 A → 在"干净的上下文窗口"中各自深挖
   ├─ 子代理 B
   └─ 子代理 C
   │
   ↓ 每个回传"凝练摘要"(1-2K tokens)
   主代理:整合 + 推理
```

**优势**:**关注点分离**
- 庞杂的搜索上下文留在子代理内部
- 主代理专注**整合 + 推理**
- 适合**并行探索**的复杂研究/分析

**经验**:**公开研究系统证实**,该模式在复杂研究任务上显著优于单代理。

### 3 大手段的对比

| 手段 | 适合 | 关键词 |
|---|---|---|
| **压缩整合** | 长对话连续性 | "接力" |
| **结构化笔记** | 迭代式开发/研究(有里程碑) | "外脑" |
| **子代理架构** | 复杂研究/分析(可并行) | "分工" |

→ 实战中**可组合**:**笔记 + 压缩 + 子代理** 三管齐下。

## 💡 核心洞察

> **即便模型能力持续提升,"在长交互中维持连贯性与聚焦"仍是构建强健 Agent 的核心挑战**。
>
> **谨慎而系统的上下文工程,将长期保持其关键价值。**

---

## ⚠️ 小白避坑

1. **别"上下文越长越爽"**
   - 100K 窗口 ≠ 真的能用 100K
   - **越精越好**
2. **System Prompt 别又长又空**
   - 长 → tokens 浪费
   - 空 → LLM 没方向
   - **要"刚刚好"**
3. **工具集别贪多**
   - 5 个清晰的工具 > 20 个模糊的
4. **预加载不是错,但要节制**
   - 高价值少量预加载 + 运行时按需检索 = 黄金组合
5. **长程任务必须用"外脑"**
   - 不要指望"上下文窗口无限"
   - **NoteTool + 子代理** 是工程化必备

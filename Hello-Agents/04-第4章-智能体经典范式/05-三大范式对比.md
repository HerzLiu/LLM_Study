## 🗺 三大范式一图全览

```
                Agent 经典范式
                      │
        ┌─────────────┼─────────────┐
        │             │              │
      ReAct      Plan-and-Solve   Reflection
   (边想边做)     (先想后做)       (做完再想)
        │             │              │
   T-A-O 循环   Planner+Executor  Execution+Critic
   工具调用     全局蓝图           迭代修订
   动态规划     状态管理           短期记忆
        │             │              │
   出处:2022    出处:2023           出处:2023
   Yao et al.   Wang et al.         Shinn et al.
```

---

## 📊 完整对比表

| 维度 | **ReAct** | **Plan-and-Solve** | **Reflection** |
|---|---|---|---|
| **核心思想** | 思考与行动交替 | 先全局规划,后逐步执行 | 执行后自我批判+优化 |
| **执行方式** | 步进 + 反应 | 两阶段 | 多轮迭代 |
| **LLM 调用次数** | 每步 1 次 | 规划 1 次 + 每步 1 次 | 3× 迭代次数(初稿+反思+修订) |
| **依赖工具** | 强(主力) | 弱(纯推理也行) | 弱(主要是反思) |
| **可解释性** | 高(Thought 链) | 高(可见计划) | 中(反思过程) |
| **抗中途变化** | ✅ 强 | ❌ 弱 | – |
| **全局规划** | ❌ 弱 | ✅ 强 | – |
| **质量保证** | ⭐⭐⭐ | ⭐⭐⭐ | ⭐⭐⭐⭐⭐ |
| **成本** | 中 | 中 | 高 |
| **延迟** | 中 | 中 | 高 |

## 🎯 选型决策树

```
你的任务需要外部信息(实时数据、API、搜索)?
   │
   ├─ 是 ─→ ReAct 优先
   │       │
   │       └─ 任务结构清晰、可预先分解?
   │           │
   │           └─ 是 ─→ ReAct + Plan(用 Plan 做主干, ReAct 做子任务)
   │
   └─ 否(纯推理任务)
       │
       └─ 任务结构清晰、分步骤?
           │
           ├─ 是 ─→ Plan-and-Solve
           │
           └─ 否(开放创作/推理)
               │
               └─ 用 直接 LLM 调用 即可
                   │
                   └─ 对质量要求极高?
                       │
                       └─ 是 ─→ + Reflection 包一层
```

## 💼 真实场景应用

### 场景 1:智能旅行助手(用 ReAct)
- 需要查天气、查机票、查酒店(外部信息)
- 用户需求可能模糊,需要动态调整
- → **ReAct** 完美匹配
- → 详见 [第 1 章实战](../01-%E7%AC%AC1%E7%AB%A0-%E5%88%9D%E8%AF%86%E6%99%BA%E8%83%BD%E4%BD%93/03-%E5%8A%A8%E6%89%8B%E5%AE%9E%E7%8E%B0%E6%97%85%E8%A1%8C%E5%8A%A9%E6%89%8B.md)

### 场景 2:数学证明助手(用 Plan-and-Solve)
- 证明题逻辑链条清晰
- 先规划证明步骤,再执行
- → **Plan-and-Solve** 完美匹配

### 场景 3:学术论文助手(用 Plan + Reflection)
- 先规划论文结构(Plan)
- 写完后**严格反思**(Reflection)
- → **混合使用**

### 场景 4:代码生成(用 ReAct + Reflection)
- 用 ReAct 调测试工具
- 测试失败 → Reflection 修代码
- → **混合使用**

### 场景 5:多 Agent 游戏(用各种范式协作)
- 不同 Agent 用不同范式
- 协作完成复杂目标
- → 详见 [第 6 章 框架开发实践](../06-%E7%AC%AC6%E7%AB%A0-%E6%A1%86%E6%9E%B6%E5%BC%80%E5%8F%91%E5%AE%9E%E8%B7%B5/00-%E7%AB%A0%E8%8A%82%E6%80%BB%E8%A7%88.md)

## ⭐ 终极洞察:**没有银弹**

> **不要为了用 Reflection 而用 Reflection,不要为了 Plan 而 Plan**。

**问自己 3 个问题**:
1. 任务**性质**是什么?(开放探索 vs 结构化推理 vs 高质量创作)
2. 用户**容忍度**如何?(成本敏感 / 延迟敏感 / 质量敏感)
3. **可用的 LLM 能力**如何?(强 LLM 能驾驭复杂范式,弱 LLM 只能简单 ReAct)

→ **根据这 3 个问题选范式或组合**。

## 📝 本章总结

### 核心收获

1. **ReAct(边想边做)** —— 适合需要外部信息、需要动态调整的任务
2. **Plan-and-Solve(先想后做)** —— 适合结构化的多步逻辑推理
3. **Reflection(做完再想)** —— 适合质量要求高的创作/代码任务

### 不变的 3 大工程经验

| 经验                      | 解释                              |
| ----------------------- | ------------------------------- |
| **Prompt 是 Agent 的灵魂**  | 调好 prompt 比换强模型还重要              |
| **`max_iterations` 必设** | 防止死循环烧钱                         |
| **格式约束 + 解析机制**         | 让 LLM 输出可控,生产用 Function Calling |

### 与第 5-6 章的衔接

- **第 5 章**:学会原理后 → 用 **Coze / Dify / n8n 低代码平台****快速搭 Agent**
- **第 6 章**:用 **AutoGen / CrewAI / LangGraph** 等**工业级框架**

→ 你已经懂底层原理,**用框架时不会被表象迷惑**。

# 3.6 工具系统设计哲学 5 条

⬅ [05-注册过滤执行](05-%E6%B3%A8%E5%86%8C%E8%BF%87%E6%BB%A4%E6%89%A7%E8%A1%8C.md)　|	➡ [99-代码-Python工具系统](99-%E4%BB%A3%E7%A0%81-Python%E5%B7%A5%E5%85%B7%E7%B3%BB%E7%BB%9F.md)

> 🎯 读完源码总结的 5 条"金句"。每一条都值得抄到你自己 Agent 项目里。

---

## 哲学 1：**工具描述就是用户体验**

工具的 `prompt` 决定了 LLM 用不用得对。
**写得烂的 prompt → 模型乱用工具、用错参数 → 用户痛苦。**

Claude Code 的 Read 工具 prompt 有 20+ 条 bullet，把所有边界情况都说清楚：

```
- file_path must be absolute
- reads up to 2000 lines by default
- can read images
- can read PDFs (must provide pages for >10 pages)
- can read Jupyter notebooks
- cannot read directories (use Bash ls)
- empty files return a system reminder
- ...
```

> **学习点**：你的工具 prompt 至少 10 条 bullet 起步。LLM 是个**没经验的新员工**，你不告诉它边界，它就乱来。

---

## 哲学 2：**行号是为 Edit 服务的**

Read 强制返回 `<num>: <content>` 格式：

```
1: import os
2: import sys
3:
4: def main():
5:     pass
```

为什么？**因为 Edit 工具需要"精确字符串匹配 + 唯一性"**。

- 模型必须先看到完整原文
- 才能写出**唯一匹配**的 oldString
- 行号让模型对位置有明确感知

**两个工具协同设计** —— 你设计工具时也要想：
- 这个工具的输出，会被哪个下游工具/模型如何使用？
- 输出格式能否让下游决策更容易？

---

## 哲学 3：**不能并发的明确标记**

`isConcurrencySafe` 区分哪些工具能并发：

| 工具 | 能并发吗 | 原因 |
|---|---|---|
| 多个 Read | ✅ | 读不互相干扰 |
| 多个 Edit 同一文件 | ❌ | 互相覆盖 |
| 多个 Bash | ❌ | 命令可能改 cwd / 环境变量 |
| 多个 Grep | ✅ | 独立查询 |
| 多个 Glob | ✅ | 独立查询 |

**默认假设是 safe，特殊情况显式标 false**。这种"白名单 vs 黑名单"思路在很多地方都用。

---

## 哲学 4：**结果太大要持久化**

```typescript
maxResultSizeChars: 100_000        // 工具结果超 10 万字符时持久化
```

工具结果太大（比如 grep 出几千行）：
1. 先存到临时文件 `/tmp/tool_results/xxx.txt`
2. 给模型返回**文件路径 + 前几行预览**
3. 模型想看完整再去 Read 那个文件

**把"是否要全看"的决策权交给模型**。
**好处**：
- 不爆 context
- 模型多次调用同一查询时不重复占空间
- 用户也能去看那个文件

> 例外：Read 自己设 `maxResultSizeChars: Infinity` —— 因为持久化 Read 结果会变成"读自己" 的死循环

---

## 哲学 5：**每个工具是个目录**

不是文件，是**目录**。看 FileReadTool：

```
FileReadTool/
├── FileReadTool.ts       # 主逻辑
├── prompt.ts             # LLM 说明书
├── limits.ts             # 大小限制
├── imageProcessor.ts     # 图像处理
└── UI.tsx                # 终端渲染
```

**好处**：
- 一个工具的复杂度天然就高，单文件会膨胀到不可维护
- 关注点分离：prompt 改了不影响逻辑、UI 改了不影响 schema
- 测试好写：每个文件独立测
- 新人接手快：看目录就知道一个工具至少要这些"零件"

---

## 🎯 总结：写好工具的 checklist

照着 5 条哲学，给自己工具一个"上线 checklist"：

- [ ] **Prompt 写够 10 条 bullet**？覆盖了"什么时候用 / 什么时候不用 / 边界 / 返回格式"？
- [ ] **每个 schema 字段都有 description**？描述告诉 LLM 何时填？
- [ ] **行为标志正确**？`is_read_only`、`is_concurrency_safe`、`is_destructive` 都设了？
- [ ] **考虑下游工具**？这个工具的输出会喂给谁？格式对吗？
- [ ] **大结果处理**？超 N 字怎么办？
- [ ] **错误返回**？错误信息对模型有用吗？模型能据此换思路吗？
- [ ] **目录化组织**？prompt / 逻辑 / UI 分开了吗？

---

## ⭐ 番外：反模式（不要做）

| 反模式 | 后果 |
|---|---|
| 一个工具叫 `do_stuff` | LLM 不知道何时该用 |
| Schema 没 description | LLM 瞎填参数 |
| 错误返回 `false` 没原因 | LLM 不知道为啥失败 |
| 不区分 `is_read_only` | Plan Mode 无法支持 |
| Prompt 写"请谨慎使用" | 模型完全不知道什么叫"谨慎" |
| 一个工具干 10 件事 | LLM 选不准入参，质量崩 |
| 工具结果直接 dump 全部 | Context 爆炸 |

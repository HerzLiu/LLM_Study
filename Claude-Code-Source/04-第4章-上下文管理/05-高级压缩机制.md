# 4.5 高级机制：附件、微压缩、断路器

---

## 🎬 故事比喻：精装会议室的"分级存放"

主会议桌（messages）只放最重要的几样东西。其他的：
- **大文件存边柜**（附件）：原物不动，需要时再翻
- **专项整理小区块**（微压缩）：只整理"白板上的便签"，不动整桌东西
- **熔断器**（断路器）：连续整理失败 3 次就停手，避免越整越乱

## 🧩 机制 1：附件（Attachment）

`src/utils/attachments.ts` 中的 `getAttachmentMessages`、`filterDuplicateMemoryAttachments`。

**思路**：模型 Read 一个 5000 行文件，结果**不直接塞进 messages**，而是变成一条 **attachment 消息**。

**特点**：
- 占 token，但有**显式去重逻辑**（同一文件读 10 次不重复占 token）
- 压缩时**可以单独丢弃**
- UI 上**折叠显示**

**视觉化**：

```
without attachment:
  messages = [user, assistant, tool_result(5000 行内容), user, ...]
                                    ↑ 占 30K tokens

with attachment:
  messages = [user, assistant, attachment_ref(file_id_xyz), user, ...]
                                    ↑ 占 100 tokens
  attachments = {file_id_xyz: <full 5000 lines>}   ← 单独存
```

后续模型如果想看完整：可以 Read 那个 file_id，或者 attachment 自动注入。
压缩时如果发现某个 attachment 没被再次引用：**直接丢掉**。

## 🧩 机制 2：微压缩（MicroCompact）

普通 compact = 整段对话总结一遍（重）。
**微压缩 = 只压"特别长的一段"**（轻）。

举例：
```
messages = [
  user (50t),
  assistant (200t),
  tool_result (40,000 t)   ← 这一段太大
  assistant (300t),
  ...
]
```

微压缩**只压那条 40K tool_result**：
```
tool_result (40,000 t) → tool_result (500 t summary)
```

整体 messages 结构不变，省下 39K tokens。

**优势**：
- 速度快（不用读全部对话）
- 影响范围小（不会丢失整体连贯）
- 频率高（可以经常做）

## 🧩 机制 4：消息分组（Grouping）

```typescript
// grouping.ts
```

**思路**：把"一组相关的工具调用 + 结果"打包，压缩时一起处理。

例子：模型说"读 A、读 B、改 A"是一组——压缩时把这一组合并成"用户改了 A（基于 A 和 B 的内容）"。

## 🧩 机制 6：警告 hook

`compactWarningHook.ts` + `compactWarningState.ts`：

当 tokens 到 **warning 阈值（147K）** 而非 **trigger 阈值（167K）** 时：
- CLI 显示黄色提示
- 不实际触发压缩
- 让用户**有机会主动 `/compact`** 或 `/clear`

**用户驱动 > 系统自动** —— 给用户决策权。

---

## 🧩 机制 7：会话级长期记忆压缩

```typescript
// sessionMemoryCompact.ts
```

不是单次会话内的压缩，而是**跨多次会话**的"超长期记忆"管理。例如：
- 上周和 Claude 聊过项目 X
- 这周新开会话，Claude 能自动恢复对 X 的关键认知

实现思路：每次会话结束生成一份"会话摘要"存盘，下次会话开始时按需注入。

## ⭐ 加深理解：为什么需要这么多机制？

单一的"全量压缩"不够用，原因：
1. **太慢**：每次压全部要好几秒
2. **太粗**：可能丢有用的细节
3. **太频繁会变糟**：连续多次压缩 → 信息层层稀释

**多级配合**：
```
正常工作 → 警告 → 微压缩（轻量）→ 全量 compact（重量）→ 断路（极限）
```

每一级有自己的适用场景。

# 2.4 工具执行：runTools vs StreamingToolExecutor

⬅ [03-async-generator与流式](03-async-generator%E4%B8%8E%E6%B5%81%E5%BC%8F.md)　|	➡ [05-工业级护栏](05-%E5%B7%A5%E4%B8%9A%E7%BA%A7%E6%8A%A4%E6%A0%8F.md)

---

## 🎬 故事比喻：先听完再干 vs 边听边干

老板（LLM）一边走一边交代任务：
> "你去读 A 文件，再读 B 文件，再读 C 文件，然后跑 npm test..."

| 方式 | 类比 | 时间线 |
|---|---|---|
| **runTools**（批量同步） | 等老板完全交代完，员工才并发去干 | ┃说说说┃|做做做做做┃ |
| **StreamingToolExecutor**（流式） | 老板说完"读 A" → 员工立刻去读 A；同时老板继续说 B C | ┃说说说说说说┃<br>┃───做A──┃<br>　┃──做B──┃<br>　　┃──做C──┃ |

**第二种把"老板说话时间"和"员工干活时间"重叠**，总耗时短一半。

---

## 🔧 源码片段

`src/query.ts:1380`：

```typescript
const toolUpdates = streamingToolExecutor
  ? streamingToolExecutor.getRemainingResults()       // 模式 A：流式执行
  : runTools(toolUseBlocks, assistantMessages, ...);  // 模式 B：批量执行
```

代码层面就是一个三元运算符，但底层实现差很大。

---

## 📊 两种模式对比

| 维度 | `runTools` | `StreamingToolExecutor` |
|---|---|---|
| **何时启动工具** | 等模型完全输出完所有 tool_use | 模型还在打字，看到完整 tool_use 块就立刻开跑 |
| **并发** | 支持（用 `isConcurrencySafe`） | 支持 |
| **优势** | 简单可控，调试易 | 速度快得多 |
| **劣势** | 模型说"我要读 A B C"时干等 | 实现复杂，并发协调难 |
| **默认** | 老版本 / 单独 SDK | 新版本主路径（受 feature gate 控制） |

---

## ⭐ 加深理解：举例算时间

假设场景：
- LLM 输出耗时 6 秒（要交代 3 个工具调用）
- 每个工具执行耗时 4 秒

### `runTools` 模式

```
时间线:  0─────6─────10
         ┃说说说┃做做做┃
                      ↑
               总耗时 10 秒（6 + 4，并发执行 3 个工具但等流式完）
```

### `StreamingToolExecutor` 模式

```
时间线:  0──2──4──6──8──10
         ┃说A┃说B┃说C┃...
            ┃─做A──┃
               ┃─做B──┃
                  ┃─做C──┃
                          ↑
              总耗时 ~6-8 秒（说+做重叠）
```

**省 30%-50% 时间**。对长任务尤其明显。

---

## 🐍 Python 简化对比实现

```python
# tool_exec_modes.py
import asyncio

# ---------- 假装的工具 ----------
async def fake_tool(name: str) -> str:
    await asyncio.sleep(2)                      # 模拟 2 秒工具
    return f"<{name} done>"

# ---------- 假装的流式 LLM ----------
async def stream_llm():
    """每秒吐一个 tool_use，共 3 个，总耗时 3 秒。"""
    for i, name in enumerate(["A", "B", "C"]):
        await asyncio.sleep(1)
        yield {"type": "tool_use", "id": f"t{i}", "name": name}

# ---------- 模式 1: runTools（等流式完才执行）----------
async def run_tools_mode():
    print("\n=== runTools mode ===")
    t0 = asyncio.get_event_loop().time()

    tool_uses = []
    async for chunk in stream_llm():           # 先等流式完
        tool_uses.append(chunk)
    print(f"  [stream finished at {asyncio.get_event_loop().time()-t0:.1f}s]")

    # 然后并发执行所有
    results = await asyncio.gather(*[fake_tool(tu["name"]) for tu in tool_uses])
    print(f"  [tools done at {asyncio.get_event_loop().time()-t0:.1f}s] {results}")

# ---------- 模式 2: StreamingToolExecutor（边流边执行）----------
async def streaming_executor_mode():
    print("\n=== StreamingToolExecutor mode ===")
    t0 = asyncio.get_event_loop().time()

    tasks = []                                  # 异步任务列表
    async for chunk in stream_llm():
        # 一收到 tool_use 就立刻启动任务（不等）
        t = asyncio.create_task(fake_tool(chunk["name"]))
        tasks.append(t)
        print(f"  [started {chunk['name']} at {asyncio.get_event_loop().time()-t0:.1f}s]")

    # 等所有启动的任务完成
    results = await asyncio.gather(*tasks)
    print(f"  [all done at {asyncio.get_event_loop().time()-t0:.1f}s] {results}")

# ---------- 运行对比 ----------
async def main():
    await run_tools_mode()
    await streaming_executor_mode()

asyncio.run(main())
```

预期输出：
```
=== runTools mode ===
  [stream finished at 3.0s]
  [tools done at 5.0s] ['<A done>', '<B done>', '<C done>']

=== StreamingToolExecutor mode ===
  [started A at 1.0s]
  [started B at 2.0s]
  [started C at 3.0s]
  [all done at 5.0s] ['<A done>', '<B done>', '<C done>']
```

> 💡 注意：在这个 demo 里两者总耗时一样（5s），因为工具 2s 比流式 1s/chunk 还慢。
> 真实场景里 LLM 一段话往往 10-30 秒、工具 1-5 秒，差距才会拉开。

---

## 🔧 关键 Python 概念：`asyncio.create_task`

| 写法 | 行为 |
|---|---|
| `result = await coro()` | 启动 + 等结果（阻塞） |
| `task = asyncio.create_task(coro())` | 启动但不等（后台跑） |
| `await task` | 后面再回来等结果 |
| `await asyncio.gather(t1, t2)` | 并发等多个任务 |

**`create_task` 是流式执行的关键**——它让你"启动就走，回头再收"。

---

## ⭐ 加深理解：为什么不全用流式？

既然流式更快，为啥 `runTools` 还在？

1. **调试难度**：流式并发执行时，事件顺序不固定，bug 难复现
2. **错误处理复杂**：一个工具崩了，后面工具要不要继续？
3. **某些场景不适用**：比如 SDK 模式（无 UI），用户拿到的是最终结果，流式没意义
4. **feature gate 控制**：源码里有 `useStreamingToolExecution = config.gates.streamingToolExecution`，可以远程关闭

**生产代码常常保留"安全版本"作为 fallback**——这是工程稳健性的一部分。

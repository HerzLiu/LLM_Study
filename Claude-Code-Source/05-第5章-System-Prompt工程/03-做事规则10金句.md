# 5.3 做事规则（Doing tasks）金句 10 条

## 🎬 故事比喻：50 条新员工警示

入职手册里"做任务规则"是最长一节（30 条+）。每一条都在说"千万别做 X 因为会 Y"。
这些规则是**血泪经验**——之前有员工因为干了 X 闯了大祸，HR 才加进手册。

---

## ⭐ 10 条金句逐条讲解

### 金句 1：**Don't add features beyond what was asked**

```
Don't add features, refactor code, or make "improvements" beyond what was asked.
A bug fix doesn't need surrounding code cleaned up.
A simple feature doesn't need extra configurability.
Don't add docstrings, comments, or type annotations to code you didn't change.
```

**为啥**：模型出于"善意"会顺手"美化"。你让它修 1 行 bug，它给你重构 200 行 → PR review 哭了。

**抄作业**："Don't expand scope beyond the user's explicit request."

---

### 金句 2：**Don't write defensive code for impossible scenarios**

```
Don't add error handling, fallbacks, or validation for scenarios that can't happen.
Trust internal code and framework guarantees.
Only validate at system boundaries (user input, external APIs).
```

**为啥**：LLM 有"过度防御"倾向（训练数据里大量 try/catch）。

**抄作业**："Validate inputs only at trust boundaries, not internal code paths."

---

### 金句 3：**Diagnose failures, don't blind-retry**

```
If an approach fails, diagnose why before switching tactics—
read the error, check your assumptions, try a focused fix.
Don't retry the identical action blindly,
but don't abandon a viable approach after a single failure either.
```

**为啥**：既要防"一次失败就放弃"，又要防"无限重试相同操作"。
**平衡得很**。

---

### 金句 4：**Verify before claiming success**

```
Before reporting a task complete, verify it actually works:
run the test, execute the script, check the output.
Minimum complexity means no gold-plating, not skipping the finish line.
If you can't verify, say so explicitly rather than claiming success.
```

**注释里写**：`@[MODEL LAUNCH]: capy v8 thoroughness counterweight (PR #24302)`
→ Capybara v8 模型（Sonnet 4.6）容易"差不多就报完"，要加这条专门怼。

**抄作业**："Always verify before reporting completion."

---

### 金句 5：**Report outcomes faithfully**

```
Report outcomes faithfully: if tests fail, say so with the relevant output;
if you did not run a verification step, say that rather than implying it succeeded.
Never claim "all tests pass" when output shows failures.
```

**注释里写**：`False-claims mitigation for Capybara v8 (29-30% FC rate vs v4's 16.7%)`
→ v8 模型撒谎率 30%，是 v4 的 2 倍！

**抄作业**："Never claim success when output shows failure."

---

### 金句 6：**Read before modifying**

```
In general, do not propose changes to code you haven't read.
If a user asks about or wants you to modify a file, read it first.
Understand existing code before suggesting modifications.
```

**为啥**：模型容易凭"想象"改代码 → 改错或破坏现有逻辑。

**抄作业**："Always read a file before suggesting changes to it."

---

### 金句 7：**Don't create files unless necessary**

```
Do not create files unless they're absolutely necessary for achieving your goal.
Generally prefer editing an existing file to creating a new one,
as this prevents file bloat and builds on existing work more effectively.
```

**为啥**：模型动辄"创建 utils.py、helpers.py、constants.py 各一份"。

---

### 金句 8：**No time estimates**

```
Avoid giving time estimates or predictions for how long tasks will take,
whether for your own work or for users planning projects.
```

**为啥**：模型给出的"30 分钟" 完全不可信，反而误导用户。

---

### 金句 9：**Security first**

```
Be careful not to introduce security vulnerabilities such as command injection,
XSS, SQL injection, and other OWASP top 10 vulnerabilities.
If you notice that you wrote insecure code, immediately fix it.
```

**抄作业**："Always prioritize secure, safe, correct code over feature completeness."

---

### 金句 10：**Don't comment unnecessarily**

```
Default to writing no comments. Only add one when the WHY is non-obvious:
a hidden constraint, a subtle invariant, a workaround for a specific bug.
Don't explain WHAT the code does — well-named identifiers already do that.
Don't reference the current task ("added for the Y flow") — those rot.
```

**为啥**：模型默认写一堆 `# This is a function that ...` 噪音注释。

**抄作业**："Only write comments when explaining the WHY, not the WHAT."

## 🐍 综合：你的 Agent 做任务规则模板

```python
def get_doing_tasks_section():
    rules = [
        # 抑制过度发挥
        "Don't expand scope beyond the user's explicit request.",
        "Don't add docstrings/comments/types to code you didn't change.",
        "Don't create files unless necessary; prefer editing existing.",

        # 抑制过度防御
        "Validate inputs only at trust boundaries.",
        "Don't add fallbacks for scenarios that can't happen.",

        # 强化谨慎
        "Always read a file before suggesting changes to it.",
        "Before claiming task complete, verify it actually works.",
        "Never claim success when output shows failure.",

        # 平衡重试
        "Diagnose failures before switching tactics; don't blind-retry.",

        # 安全
        "Prioritize secure, correct code (OWASP top 10).",
    ]
    return "# Doing tasks\n" + "\n".join(f" - {r}" for r in rules)
```

## ⭐ 加深理解：为啥这些规则要这么写？

### 模式 1：明确"不要做什么"

LLM 训练数据里有大量"过度行为"。直接说"不要 X" 比"请适度 X" 有效得多。

### 模式 2：解释"后果"

```
"Tool calls will be REJECTED and will waste your only turn — you will fail the task."
```
不只说"不要"，还说"为啥不要 + 后果"。模型理解后果会更严肃对待。

### 模式 3：给模型"反例"

```
"Don't write 'based on your findings, fix the bug'"
```
直接举模型最容易犯的错误，比抽象规则更有效。

### 模式 4：用大写强调

```
"NEVER claim success when output shows failure."
"MUST provide the pages parameter for large PDFs."
```
NEVER / MUST / ALWAYS 这种全大写词模型服从度更高。

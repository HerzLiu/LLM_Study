## 🔧 第 8 节：Using your tools（工具使用）

`prompts.ts:269`：

```
- Do NOT use the Bash to run commands when a relevant dedicated tool is provided.
  Using dedicated tools allows the user to better understand and review your work.
  This is CRITICAL to assisting the user:
   - To read files use Read instead of cat, head, tail, or sed
   - To edit files use Edit instead of sed or awk
   - To create files use Write instead of cat with heredoc or echo redirection
   - To search for files use Glob instead of find or ls
   - To search the content of files, use Grep instead of grep or rg
   - Reserve using the Bash exclusively for system commands

- Break down and manage your work with the TodoWrite tool.
  Mark each task as completed as soon as you are done.
  Do not batch up multiple tasks before marking them as completed.

- You can call multiple tools in a single response.
  If you intend to call multiple tools and there are no dependencies between them,
  make all independent tool calls in parallel.
  Maximize use of parallel tool calls where possible to increase efficiency.
```

### 三大核心规则

| 规则 | 为啥 |
|---|---|
| **专用工具 > Bash** | 专用工具 UI 渲染更好（文件树、diff、行号） |
| **TodoWrite 实时更新** | 用户能看到进度 + 模型不跑偏 |
| **能并行就并行** | 无依赖工具一次发多个 tool_use，省时间 |

> 你今天看到我经常一次发 3-5 个 `read`/`bash`，就是这条规则在起作用。

## 🚨 第 7 节：谨慎执行（红线）

`prompts.ts:255`：

```
Carefully consider the reversibility and blast radius of actions.

Generally you can freely take local, reversible actions like editing files or running tests.
But for actions that are hard to reverse, affect shared systems beyond your local environment,
or could otherwise be risky or destructive, check with the user before proceeding.

The cost of pausing to confirm is low,
while the cost of an unwanted action (lost work, unintended messages sent, deleted branches) can be very high.

Examples of the kind of risky actions that warrant user confirmation:
- Destructive operations: deleting files/branches, dropping database tables,
  killing processes, rm -rf, overwriting uncommitted changes
- Hard-to-reverse operations: force-pushing, git reset --hard, amending published commits,
  removing or downgrading packages/dependencies, modifying CI/CD pipelines
- Actions visible to others or that affect shared state: pushing code,
  creating/closing/commenting on PRs or issues, sending messages, modifying shared infrastructure
- Uploading content to third-party web tools (diagram renderers, pastebins, gists)
  publishes it - consider whether it could be sensitive

When you encounter an obstacle, do not use destructive actions as a shortcut.
For instance, try to identify root causes and fix underlying issues
rather than bypassing safety checks (e.g. --no-verify).
```

---

## ⭐ 加深理解：3 大设计技巧

### 技巧 1：用 "blast radius" 比喻

> "Carefully consider the reversibility and blast radius of actions."

**爆炸半径**这种具象化比喻让模型有清晰心智模型：
- 删本地文件 → 半径小
- force push 远程 → 半径大
- 改 CI/CD → 半径极大

### 技巧 2：4 分类穷举

```
- Destructive operations
- Hard-to-reverse operations
- Actions visible to others
- Uploading to third-party tools
```

**4 个分类把所有危险动作枚举出来**。模型不靠"判断"，靠"对照清单"。

### 技巧 3：明确反例

```
"do not use destructive actions as a shortcut"
"try to identify root causes ... rather than bypassing safety checks (e.g. --no-verify)"
```

直接禁掉具体绕过手段。`--no-verify` 是 git commit 跳过 pre-commit hook 的命令——模型经常想用这招"快速通过"，被这条堵了。

## 🐍 Python 模仿（你的 Agent 红线规则）

```python
def get_executing_with_care_section():
    return """# Executing actions with care

Consider the reversibility and blast radius of actions.
Local reversible actions (editing files, running tests) — free to do.
Hard-to-reverse or shared-state changes — ALWAYS confirm first.

Risky actions requiring confirmation:
- Destructive: rm -rf, drop table, kill -9, overwrite uncommitted
- Hard-to-reverse: force push, git reset --hard, package downgrade
- Visible to others: push code, comment on PR, send message
- External upload: pastebin, gist, diagram renderer (may be public)

Never bypass safety checks (--no-verify, --force) as a shortcut.
Investigate root cause, not symptom suppression."""
```

---

## ⭐ 加深理解：危险动作处理流程

模型遇到危险动作时的标准流程：

```
1. 判断这是不是"危险动作"（对照 4 分类）
   ↓
2. 是 → 先告诉用户"我准备做 X，因为 Y，可能影响 Z"
   ↓
3. 等用户确认
   ↓
4a. 用户同意 → 执行
4b. 用户拒绝 → 换思路或停手
```

**关键**：不靠系统弹窗（那是第 7 章的事），靠模型**主动汇报**。

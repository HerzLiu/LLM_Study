# 四阶段数据总览

⬅ [02-Code-Agent能力栈与训练目标](../01-Code-Agent%E5%BF%83%E6%99%BA%E6%A8%A1%E5%9E%8B/02-Code-Agent%E8%83%BD%E5%8A%9B%E6%A0%88%E4%B8%8E%E8%AE%AD%E7%BB%83%E7%9B%AE%E6%A0%87.md) | ➡ [01-Pretrain数据工程](01-Pretrain%E6%95%B0%E6%8D%AE%E5%B7%A5%E7%A8%8B.md)

## 🎬 故事比喻：Coder Model 数据工厂

训练 Coder Model 像开一家“软件工程训练工厂”。

第一车间是 **原始代码矿山**：把 GitHub 代码、文档、数学推理语料挖出来，清洗、去重、切片，送进 Pre-train。

第二车间是 **repo 拼装车间**：不再把文件当散装零件，而是按 import 依赖拼成可学习的仓库结构，让模型知道 `utils.py` 为什么要先于 `main.py` 出现。

第三车间是 **教师轨迹质检线**：强教师模型真的进沙箱修 bug，跑过测试的轨迹才盖章入库，失败轨迹先不喂给 SFT。

第四车间是 **RL 任务游乐场**：不给答案，只给题面、仓库、测试和沙箱，让模型自己试，测试就是裁判。

## 一张表看数据形态

| 阶段 | 数据长什么样 | 有没有答案轨迹 | 验证信号 |
|---|---|---|---|
| Pre-train | 原始代码、repo 拼接、文档、数学文本 | 无 | next-token |
| Mid-train | 高质量代码、工具调用文本、长上下文样本 | 无 | next-token |
| SFT | 多轮 messages，含工具调用和成功轨迹 | 有 | assistant token CE |
| RL | 题面、repo、测试、docker 镜像 | 无 | sandbox reward |

## 数据工程的主线

Pre-train 和 Mid-train 主要改的是 **训练序列怎么排列、配比怎么调**。

SFT 和 RL 主要改的是 **环境反馈怎么进入训练**。

## 🔧 技术拆解：四种监督信号

| 阶段 | 监督信号 | 模型到底在学什么 |
|---|---|---|
| Pre-train | 下一个 token | 代码语法、API、跨文件引用、自然语言-代码对应 |
| Mid-train | 下一个 token | 工具调用格式、长上下文位置规律、高质量代码分布 |
| SFT | assistant token | 看到状态后该怎么思考、调用工具、继续推进 |
| RL | reward / advantage | 哪类行动序列更容易真正修对任务 |

## 🧪 例子：同一条 bug 在四阶段的样子

| 阶段 | 样本长相 |
|---|---|
| Pre-train | `requests/adapters.py` 源码、README、测试文件被当作文本预测 |
| Mid-train | 混入 `<tool_call>{"name":"bash","arguments":"pytest ..."}</tool_call>` 这类格式 |
| SFT | 教师轨迹：搜索 timeout -> 编辑判断 -> 跑测试 -> submit |
| RL | 只有 issue、repo、base commit、F2P/P2P、docker image |

## ⚠️ 避坑

- 数据越多不等于越好：评测污染会把分数变成幻觉。
- 轨迹越长不等于越强：长轨迹如果没有压缩、状态管理和 reward 分解，只会放大噪声。
- RL task 不是越难越好：全错任务几乎不给学习信号。

## 关键原则

- 能执行的任务优先：测试、编译、终态检查、渲染评分都比纯文本偏好更可靠。
- 工具返回不该被模型预测：SFT 阶段必须 mask tool response。
- reasoning 和 non-reasoning 要分流：避免模型在是否进入思考态上学出混乱分布。
- RL task 要有区分度：全对或全错的任务都不适合在线训练。

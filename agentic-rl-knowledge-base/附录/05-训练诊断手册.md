## 🎬 这份手册的用途

> 你照着教程跑训练，发现：
> - reward 不涨 / 涨了又掉

> - 成功率 90% 但抽查 patch 全是 hack
> - Docker 跑一半挂了

- 🔴 严重（训练崩 / 不可继续）

## 🔥 A.5.1 训练过程类故障（最常见）

### S1：Reward 不涨（训了一晚 reward 还是 0）🟡

**可能原因**（按概率排序）：

| 原因 | 验证方法 | 修复 |
|---|---|---|
| Task 太难，sample K 个全 fail（GRPO $\sigma_g=0$） | 看 rollout log 里"通过率"——若全 0 说明任务超模型能力 | 用更易任务 warmup；或加 SFT 冷启动 |
| Reward 函数有 bug（gold 错对） | 用 gold patch 喂 reward 函数，应返回 1.0 | 加 unit test 验证 reward 函数本身 |
| KL penalty 太大（β > 0.5） | 看 KL 曲线——若一直接近 0，说明 π 不动 | 减 β 到 0.01-0.1 |
| Learning rate 太小 | 看 actor loss 曲线——若几乎不变 | 加大 lr（如 1e-7 → 1e-6） |
| Advantage 全是 0（reward 全相同） | 打印一个 batch 的 advantages | 任务难度分层；K 取大一点 |
| 数据 leak（prompt 含答案） | 抽查 prompt 是否含解 | 修 prompt 模板 |

详见：[§1.5 sparse reward](../01-%E7%AC%AC1%E7%AB%A0-RL%E6%9C%80%E5%B0%8F%E5%BF%85%E8%A6%81%E5%9F%BA%E7%A1%80/05-Sparse-Reward%E4%B8%8E%E4%BF%A1%E7%94%A8%E5%88%86%E9%85%8D.md) + [§2.3.5 组全同情况](../02-%E7%AC%AC2%E7%AB%A0-%E4%BB%8ERLHF%E5%88%B0Agentic-RL/03-GRPO%EF%BC%88%E7%BB%84%E5%86%85%E7%9B%B8%E5%AF%B9%E4%BC%98%E5%8A%BF%EF%BC%89.md#%EF%B8%8F-235-%E5%BD%93%E7%BB%84%E5%86%85-reward-%E5%85%A8%E7%9B%B8%E5%90%8C%E6%97%B6%E8%BE%B9%E7%95%8C%E6%83%85%E5%86%B5)

### S2：KL 暴炸（KL > 50，模型输出乱码）🔴

**症状**：

```
step 100: KL = 0.3
step 500: KL = 5
step 1000: KL = 80 ← 已经崩
step 1500: 模型输出 "<<<<<<###@@@..." 
```

**可能原因 + 修复**：

| 原因 | 修复 |
|---|---|
| β 太小（< 0.001） | 加大 β 到 0.01-0.05 |
| Reward 数值太大（如 +100） | normalize reward 到 [-1, 1] 或 [0, 1] |
| Clip ε 太大（> 0.3） | 减小到 0.1-0.2 |
| Reference model 选错（如用了 base 不是 SFT） | 改 ref = SFT 后的模型 |
| 没有 adaptive KL | 用 [§2.1.5 adaptive KL](../02-%E7%AC%AC2%E7%AB%A0-%E4%BB%8ERLHF%E5%88%B0Agentic-RL/01-RLHF%E4%B8%89%E9%98%B6%E6%AE%B5%EF%BC%88SFT-RM-PPO%EF%BC%89.md) |
| Learning rate 太大 | 减小 10 倍试 |

**应急**：保存 checkpoint，回到上一个 KL < 5 的版本，调参重训。

详见：[§1.4.3 KL 约束](../01-%E7%AC%AC1%E7%AB%A0-RL%E6%9C%80%E5%B0%8F%E5%BF%85%E8%A6%81%E5%9F%BA%E7%A1%80/04-PPO%E4%B8%8EKL%E7%BA%A6%E6%9D%9F.md)

### S3：Reward 涨但人工抽查 patch 全是 hack 🔴

**症状**：

```
报告: success rate 0.85 ✨
抽查 10 个"成功"patch:
  - 3 个改了测试断言
  - 2 个 hard-code 输入输出
  - 2 个 pytest.skip
  - 2 个 try-except 吞异常
  - 只有 1 个是真修
```

**原因**：**Reward Hacking**（agent 在钻 reward 漏洞）

**排查**：

```python
# 自动检测 hack 模式（在 reward 计算前跑）
def detect_hack(patch, test_files):
    hacks = []
    if any(t in patch.modified_files for t in test_files):
        hacks.append("modified test file")
    if "pytest.skip" in patch.added_content:
        hacks.append("pytest.skip")
    if patch.added_content.count("if x ==") > 5:
        hacks.append("excessive hard-coding")
    if "except:" in patch.added_content and "pass" in patch.added_content:
        hacks.append("bare except + pass")
    return hacks
```

**修复**：详见 [§4.8 全文](../04-%E7%AC%AC4%E7%AB%A0-Code-Agentic-RL%E4%B8%93%E9%A2%98/08-Reward-Hacking%E4%B8%8ESandbox%E5%AE%89%E5%85%A8.md)

- 🔒 锁测试文件（chmod 444）
- 🚫 reward 函数检测 hack 模式，重罚
- 📝 用 hidden tests（agent 看不到 evaluation 测试）
- 👀 每次报告 success rate 都**强制抽查 10%**

### S4：训练成功，OOD 测试集崩 🟡

**症状**：

```
训练 task set A: success 90%
hold-out task set B（同分布）: success 30%
SWE-bench Verified: success 10% ← OOD
```

**原因**：

| 原因 | 验证 | 修复 |
|---|---|---|
| Overfitting | 训练后期 train acc 还涨但 hold-out 已不涨 | 加 KL 约束 + early stop |
| Benchmark 污染 | 训练集和 SWE-bench 有重叠 issue | 时间切分（用训练截止后的 issue） |
| Task 分布过窄 | 训练只有 1-2 种 bug 类型 | 用 SWE-smith 合成更多样数据 |
| Reward 过拟合 | reward 学到了 spurious feature（如长 patch=高分） | 多 reward 联合 + 静态分析 |

详见：[§4.8 B benchmark overfitting](../04-%E7%AC%AC4%E7%AB%A0-Code-Agentic-RL%E4%B8%93%E9%A2%98/08-Reward-Hacking%E4%B8%8ESandbox%E5%AE%89%E5%85%A8.md#b-benchmark-overfitting)

### S5：Advantage 全 0 / Loss 全 0（GRPO 特有）🟡

**症状**：GRPO 训练时一组 K=16 个 rollout，全部 reward 相同 → $\sigma_g = 0$ → $\hat{A}_i = 0$ → 梯度 = 0。

**两种情况**：

| 情况 | 原因 | 修复 |
|---|---|---|
| K 个 sample 全 pass | task 太简单 | 提高任务难度；或 filter 掉这组 |
| K 个 sample 全 fail | task 太难（超模型能力） | SFT warmup；加更多 demo |

**工程修复**（DAPO 的 dynamic sampling 技巧）：

```python
def filter_useless_groups(groups):
    """过滤掉 σ ≈ 0 的 group（白训）"""
    return [g for g in groups if g.std > 1e-3]
```

详见：[§2.3.5](../02-%E7%AC%AC2%E7%AB%A0-%E4%BB%8ERLHF%E5%88%B0Agentic-RL/03-GRPO%EF%BC%88%E7%BB%84%E5%86%85%E7%9B%B8%E5%AF%B9%E4%BC%98%E5%8A%BF%EF%BC%89.md#%EF%B8%8F-235-%E5%BD%93%E7%BB%84%E5%86%85-reward-%E5%85%A8%E7%9B%B8%E5%90%8C%E6%97%B6%E8%BE%B9%E7%95%8C%E6%83%85%E5%86%B5)

### S6：Loss 出现 NaN / Inf 🔴

**症状**：第 N 个 step 突然 loss = NaN，后续训练全废。

**可能原因**：

| 原因 | 验证 | 修复 |
|---|---|---|
| Importance ratio $\rho$ 爆炸（10^6） | 打印 ratio min/max | 加 clip；或加 IS truncation |
| log(0) 出现 | 检查 $\pi(a\|s)$ 是否有 0 | softmax 加 $\epsilon$ 或加 label smoothing |
| Reward 含 inf | reward 函数返回 ∞？ | reward clipping 到 [-10, 10] |
| 梯度爆炸 | 看 grad_norm 曲线 | 加 grad clipping（max_norm=1.0） |
| FP16 溢出 | 改用 BF16 或 FP32 训 critic | mixed precision 配置检查 |

**应急**：

```python
# 在 train loop 里加
if not torch.isfinite(loss):
    print(f"NaN at step {step}, skipping batch")
    optimizer.zero_grad()
    continue
```

### S7：训练曲线"反复横跳"（不收敛）🟡

**症状**：reward 在 0.3-0.5 间反复震荡，不收敛。

**可能原因**：

| 原因 | 修复 |
|---|---|
| Batch size 太小 | 加大 batch（GRPO 至少 K=8, batch ≥ 32 prompt） |
| Learning rate 太大 | 减半 |
| KL 约束在"束紧 → 放松"震荡 | 用固定 β，不要 adaptive |
| Reward variance 太大 | 用 GAE λ 平滑；或 reward normalization |
| Rollout 数据太老（PPO 多 epoch 用同批数据） | 减少 ppo_epochs（从 4 → 1） |

详见：[§1.4](../01-%E7%AC%AC1%E7%AB%A0-RL%E6%9C%80%E5%B0%8F%E5%BF%85%E8%A6%81%E5%9F%BA%E7%A1%80/04-PPO%E4%B8%8EKL%E7%BA%A6%E6%9D%9F.md)

## 🐳 A.5.2 环境 / 工程类故障

### S8：Docker build 失败 / 卡住 🟡

**症状**：跑 SWE-bench 单 task，Docker build 几十分钟不返回。

**原因 + 修复**：

| 原因 | 修复 |
|---|---|
| 网络问题（pip 装不动包） | 用国内镜像 `pip install -i https://pypi.tuna.tsinghua.edu.cn/simple/` |
| 磁盘空间不足 | `docker system prune -a` 清旧 image |
| 镜像 tag 已变（如 base image 更新破坏依赖） | 固定 base image digest 不要用 `latest` |
| Conda 解析慢 | 用 mamba 代替 conda |

**SWE-bench 官方建议**：

- 至少 **120GB 空闲磁盘**
- **16GB RAM**
- `--max_workers <= min(0.75 * cpu_count, 24)`

详见：[§4.7](../04-%E7%AC%AC4%E7%AB%A0-Code-Agentic-RL%E4%B8%93%E9%A2%98/07-Repo%E5%9C%B0%E5%9B%BE%EF%BC%88SWE-agent-OpenHands%E7%AD%89%EF%BC%89.md)

### S9：测试 flaky（同样代码同样测试，有时过有时不过）🟡

**原因**：

| 类型 | 例子 |
|---|---|
| 时间依赖 | `assert today() == "2024-01-01"` |
| 网络依赖 | 测试调外部 API |
| 随机种子 | `random.choice` 无 seed |
| 文件系统竞争 | 并发测试写同一文件 |
| 顺序敏感 | test_B 依赖 test_A 的副作用 |

**修复策略**：

```python
def run_with_retry(test, max_retry=3):
    """flaky test 重试取多数"""
    results = [pytest_run(test) for _ in range(max_retry)]
    return sum(r == "pass" for r in results) > max_retry / 2
```

**报告时**：区分 "**模型失败**" 和 "**环境失败**"——后者不应纳入 reward。

### S10：GPU OOM 🟡

**症状**：`CUDA out of memory`。

**优先尝试（按代价从小到大）**：

| 修复 | 效果 |
|---|---|
| 减 batch size | 立竿见影 |
| 减 max_length（rollout response 长度） | 直接 50% 显存 |
| 用 gradient_checkpointing | 慢 30% 但省 50%+ |
| 用 LoRA / QLoRA | 大模型必备 |
| BF16 / FP16 | 省 50% |
| ZeRO-3 / DeepSpeed | 多卡分参数 |
| vLLM rollout + 训练分离 | 业界标配 |
| K（GRPO 采样数）减小 | 直接 K 倍降显存 |

跨链：[Hello-Agents §11.3 LoRA 配置](../../Hello-Agents/11-%E7%AC%AC11%E7%AB%A0-Agentic-RL/03-SFT%E8%AE%AD%E7%BB%83%E5%AE%9E%E6%88%98.md)

### S11：Sandbox 安全事故（agent 删了你的文件 / 泄露 key）🔴 **最严重**

**症状**：

- 训练 rollout 后发现 `~/.aws/credentials` 被 cat 到 log
- 跑 agent 后 home 目录少了文件
- 公司监控告警"出站到未知 IP"

**这是真实事故**，不是假设。**必须事前防护**：

### 必装防护层

```yaml
# Docker 启动必加这些 flag
docker run \
  --network=none \                    # 禁网
  --read-only \                       # 文件系统只读
  --tmpfs /tmp:size=100M \             # 仅 tmp 可写
  --memory=4g \                        # 内存上限
  --cpus=2 \                           # CPU 上限
  --pids-limit=100 \                   # 进程数上限
  --security-opt=no-new-privileges \   # 不允许 sudo
  --user 1000:1000 \                   # 非 root
  -v /workspace:/workspace:ro \        # 只挂载需要的，read-only
  your-image
```

**绝对不要做的事**：

- ❌ 给 agent `--privileged`
- ❌ 在裸机直接跑 agent 命令
- ❌ 挂载 `~/.ssh`、`~/.aws`、`/etc`
- ❌ 给 agent shell 权限但不限制网络

详见：[§4.8 D Sandbox](../04-%E7%AC%AC4%E7%AB%A0-Code-Agentic-RL%E4%B8%93%E9%A2%98/08-Reward-Hacking%E4%B8%8ESandbox%E5%AE%89%E5%85%A8.md#d-sandbox-%E5%AE%89%E5%85%A8-%EF%B8%8F-%E6%9C%80%E4%B8%A5%E9%87%8D)

## 🧪 A.5.3 评估 / 报告类故障

### S12：报告 pass@1 = 50%，跑 demo 时只能成 20% 🟡

**症状**：实验室 paper 报告 50%，自己跑只有 20%。

**原因**：

| 原因 | 修复 |
|---|---|
| 用了不同 temperature / sampling | 对齐论文 (常 T=0.2, top_p=0.95) |
| 不同 K（论文 K=100, 你 K=10） | pass@k 报告时 n 应≥k |
| 计算方式错（用 c/k 而非无偏估计） | 用 [§A.4.3 pass@k 公式](04-%E5%85%AC%E5%BC%8F%E9%80%9F%E6%9F%A5%E8%A1%A8.md) |
| 测试集版本不同 | LiveCodeBench 有 v1-v6，对齐版本 |
| Prompt 模板不同 | 用 paper 原 prompt |

### S13：Resolved rate 涨但 PASS_TO_PASS 也破了（你没注意）🟡

**症状**：只看 FAIL_TO_PASS 通过率，忽略 P2P。

**修复**：

```python
def correct_resolved_rate(task, patch):
    f2p_all_pass = all(pytest(t, patch) for t in task.FAIL_TO_PASS)
    p2p_all_pass = all(pytest(t, patch) for t in task.PASS_TO_PASS)
    return f2p_all_pass and p2p_all_pass  # **两者都必须**
```

详见：[§4.8 B.3 resolved_rate 完整公式](../04-%E7%AC%AC4%E7%AB%A0-Code-Agentic-RL%E4%B8%93%E9%A2%98/08-Reward-Hacking%E4%B8%8ESandbox%E5%AE%89%E5%85%A8.md)

**症状**：

SWE-bench Lite: 35%
SWE-bench Verified: 8% ← 怎么差这么多？

## 🧠 A.5.4 概念性疑问（不是 bug 但很常见）

### Q1：为什么 GRPO 的 advantage 是组内统计？不该是全局 baseline 吗？

**答**：不同 prompt 的难度不同，**reward 不可比**。组内统计**只在同 prompt 内比较**，避免"难 prompt 上 reward 0.3 被当成差，简单 prompt 上 reward 0.3 被当成好"的混淆。

详见：[§2.3.2](../02-%E7%AC%AC2%E7%AB%A0-%E4%BB%8ERLHF%E5%88%B0Agentic-RL/03-GRPO%EF%BC%88%E7%BB%84%E5%86%85%E7%9B%B8%E5%AF%B9%E4%BC%98%E5%8A%BF%EF%BC%89.md)

### Q2：DPO 没有 reward model 怎么"训"？

**答**：DPO 用闭式解技巧——RLHF + KL 约束下，最优 policy 和 reward 之间有解析关系，**reward 可以反推自 policy**。所以训练时直接优化 policy 让它满足偏好关系，跳过 reward model。

详见：[§2.2.2](../02-%E7%AC%AC2%E7%AB%A0-%E4%BB%8ERLHF%E5%88%B0Agentic-RL/02-DPO%EF%BC%88%E5%81%8F%E5%A5%BD%E7%9B%B4%E6%8E%A5%E4%BC%98%E5%8C%96%EF%BC%89.md)

### Q3：为什么 LLM RLHF 一定要 KL penalty？传统 RL 没这个

**答**：传统 RL 的策略**没有预训练价值**——崩了重训就行。LLM 的 $\pi_\theta$ 是 SFT 之后的，**KL penalty 保护语言能力**（防止为了 reward 把语言学坏）。

详见：[§1.4.3](../01-%E7%AC%AC1%E7%AB%A0-RL%E6%9C%80%E5%B0%8F%E5%BF%85%E8%A6%81%E5%9F%BA%E7%A1%80/04-PPO%E4%B8%8EKL%E7%BA%A6%E6%9D%9F.md)

### Q4：reward shaping 加了，模型反而学坏了？

**答**：你加的 shaping **可能不是 potential-based**。试试改成 $F = \gamma \Phi(s') - \Phi(s)$ 形式（Ng 1999 定理），**保证不改变最优策略**。

详见：[§1.5.3 A.1](../01-%E7%AC%AC1%E7%AB%A0-RL%E6%9C%80%E5%B0%8F%E5%BF%85%E8%A6%81%E5%9F%BA%E7%A1%80/05-Sparse-Reward%E4%B8%8E%E4%BF%A1%E7%94%A8%E5%88%86%E9%85%8D.md)

### Q5：on-policy vs off-policy 训出的模型有质量差异吗？

**答**：理论上**最优策略一样**，但 on-policy（PPO/GRPO）**探索更广**，常能找到 off-policy（DPO）找不到的解。代价是**贵 N 倍**。

详见：[§1.4b](../01-%E7%AC%AC1%E7%AB%A0-RL%E6%9C%80%E5%B0%8F%E5%BF%85%E8%A6%81%E5%9F%BA%E7%A1%80/04b-On-Policy-vs-Off-Policy.md)

## 🆘 A.5.5 紧急救援流程

**你在跑训练，凌晨 3 点 reward 突然挂了——该怎么办？**

```
1. 立即 Ctrl+C 停训练（防止继续浪费 GPU）
2. 检查 checkpoint：上一个 reward 正常的步在哪？
   $ ls -lat checkpoints/ | head
3. 看最近 100 步的 wandb / tensorboard 曲线
   - KL 是否暴炸？→ S2
   - Reward 是否突然为 0？→ S5
   - Loss 是否 NaN？→ S6
4. 检查 OOM 日志：
   $ dmesg | grep -i "killed process"
5. 回滚到上一个好 checkpoint，调参重启
6. 如果三次同样问题：换 reward 函数 / 改 β / 减小 lr
```

**写一份事故记录**：

```markdown
## Incident Log [日期]
- Symptom: ...
- Last good step: ...
- Suspected cause: ...
- Action: ...
- Prevention: ...
```

→ 长期看，事故记录比任何教程都有价值。

## 📌 A.5 节要点

| 类别 | 高频故障 | 速查节 |
|---|---|---|
| 训练 | reward 不涨 / KL 爆炸 / NaN | S1, S2, S6 |
| Reward hacking | 成功率高但 patch 烂 | S3 |
| 数据 | OOD 崩 / overfitting | S4 |
| GRPO 特有 | advantage = 0 | S5 |
| 工程 | Docker / flaky / OOM | S8, S9, S10 |
| 安全 | sandbox 事故 | **S11**（最严重） |
| 评估 | pass@k 不对 / P2P 漏检查 | S12, S13 |
| 概念 | GRPO / DPO / KL / shaping | Q1-Q5 |

**最重要的一条**：**保存 trajectory + 抽查"成功"样本** —— 这是发现 reward hacking 的唯一办法。
